# Decision Record

This document records the design decisions of Strata, a database driven from a Command-Line Interface (CLI), as Architecture Decision Records (ADR). An entry has up to five parts: the Decision, the Rationale, the Cost, the Current state (what can be observed in the system today) and the Rejected alternatives. The design is in [DesignDocument.md](DesignDocument.md) and the tests are in [TestDocument.md](TestDocument.md).

## Decisions

### ADR-0001: The engine port sits at the logical plan layer

- **Decision:** `IEngine::Execute(const PlanNode&)` takes the logical plan from the Binder. Each engine runs it with its own executor.
- **Rationale:** The project compares whole engines. With the port at the storage layer (`scan`, `lookup`, `insert`), one shared executor would sit above every engine and hide differences in operators and index choices.
- **Cost:** Each engine, flatfile included, needs its own plan executor. In return the engines can be compared on execution as well as storage.
- **Rejected:** A storage-layer port, for the reason above.

### ADR-0002: `DELETE` of a referenced row uses RESTRICT

- **Decision:** A row referenced by a foreign key of another table cannot be deleted. A `DELETE` that selects such a row returns `kConstraintViolation` and deletes nothing.
- **Rationale:** Cascading delete needs its own implementation in every engine, makes the Write-Ahead Log (WAL) record a chain of changes and multiplies the cross-engine test cases.
- **Cost:** A user has to delete the child rows first. In return every engine follows one rule.
- **Rejected:** CASCADE, for the reasons above; SET NULL, because the system has no NULL (ADR-0007).

### ADR-0003: The abstract syntax tree belongs to the Domain, and parsing stays in the Adapter

- **Decision:** The Abstract Syntax Tree (AST) types `Statement` and `Expr` live in `domain/ast.h`. `SqlParser` (Adapter) produces the AST, `Binder` (Domain) consumes it, and `QueryService::Execute` takes a `Statement`.
- **Rationale:** The Application operation is "execute one statement", so its input needs a structured form of Structured Query Language (SQL). The Binder is a pure function and can be tested in the Domain without an engine or files.
- **Cost:** The Domain holds SQL syntax structures. In return the Binder and the Application do not depend on text parsing.
- **Rejected:** Keeping the AST in the Adapter (the Application would depend on the parser); fixed query and update operations (they cannot accept every combination the syntax table allows).

### ADR-0004: flatfile loads by schema and serializes `Row` by schema on write

- **Decision:** `CsvRepository::Load` reads `catalog.csv` and parses each table's Comma-Separated Values (CSV) file into `Row` values by the `TableSchema` stored there (rules in Design Document 2.9). Two operations write: `Commit` replaces several files in one staged step (ADR-0008), and `AppendRows` appends rows. Both serialize `Row` by `TableSchema`. Rows that fail to parse are recorded by line number in `LoadedTable::rejected_lines` and reported by `.open`, because the next rewrite drops them. Loading does not check foreign keys, so those rules live only in `TableSchema::foreign_keys` (ADR-0006).
- **Rationale:** Per-column write methods cannot cover general `INSERT`, `UPDATE` and `DELETE`, and a table created with Data Definition Language (DDL) has no entity class. Dropping rows by foreign key at load time would define the rules twice and lose data silently.
- **Cost:** Orphan rows are kept and unparsable rows are not written back. In return the file equals the in-memory content, and the schema is the only source of the table definition.
- **Current state:** `.open` prints the number of rejected rows and the first 10 line numbers (Design Document 3.1). The CLI tests show it on a copy of `sample_my_db/` whose `students.csv` has three rejected lines: `students=30 (rejected 3)` on the `loaded` line and `students.csv: rejected lines 12, 17, 18` below it (ET-01). The `depots.csv` that the volume tests write has 10004 lines including the header; line 12 `x10,D00010S,Lindenworth`, line 17 `15,D00015B;Embermouth` and line 18 `15,D00015B,Embermouth,spare` are not rows of `depots` (VU-06), and an import that skips bad rows imports the other 10000 (XE-01). `parcels.csv` and `scans.csv` have no rejected rows (VU-06) and no orphan foreign key (VU-03).
- **Rejected:** One write method per updatable column (each new column needs one); filtering by foreign key at load time (the rationale above); keeping unparsable rows on write-back (it needs a map from file lines to in-memory rows).

### ADR-0005: Engine capability differences are expressed as `kUnsupported`

- **Decision:** When an engine meets a plan or data it cannot execute, such as a flatfile TEXT value that contains a newline, it returns `ExecutionError{kUnsupported, <description>}` instead of terminating. The SQL front end never branches on the engine. The Binder returns its own `kUnsupported` only for features no engine supports, such as `UPDATE` of a primary key column.
- **Rationale:** flatfile is the baseline, and the engines can differ in the plans they run. The front end is shared, so capability differences surface in the response of the port.
- **Cost:** An unsupported statement is found only when it executes. In return the front end knows nothing about any engine.
- **Current state:** flatfile returns `kUnsupported` only for TEXT that contains a newline. paged returns it for a row longer than 4060 bytes, including one that `ALTER TABLE ADD COLUMN` would create, and for a table name that starts with `sys_` (Design Document 2.8).
- **Rejected:** Checking capability in the front end (it would need to know the engine kinds); a capability query on the port (when the decision was made there was one engine, so there was nothing to query).

### ADR-0006: Referential integrity rules are declared in the schema and enforced by each engine

- **Decision:** A foreign key is declared with `REFERENCES` in `CREATE TABLE` and stored in `TableSchema::foreign_keys` (column position, referenced table, referenced column position). A referenced column must be a primary key or `UNIQUE` (ADR-0013). Updating a referenced column always cascades to the referencing rows, and deleting a referenced row is always rejected (ADR-0002). Every engine enforces these rules (rules in Design Document 2.5).
- **Rationale:** Every engine needs the same behavior, and rules kept as data can be stored by any engine that persists the catalog. A primary key cannot be updated, so a cascade happens only for a referenced `UNIQUE` column such as `visitors.username`.
- **Cost:** Each engine implements the checks itself, but the rules are data, not code.
- **Current state:** The 10000 `code` values of the volume table `depots` are distinct, so `UNIQUE` can be declared, and every `depot_code` of `parcels` and `scans` is the code of a depot. Loading checks neither `UNIQUE` nor foreign keys. When the data contains duplicate `UNIQUE` values, a cascade rewrites every referencing row that has the same value.
- **Rejected:** Hard-coding the rules in a column handler (one handler per rule); a shared enforcement function in the Domain (it needs engine data and breaks the port boundary); an update action on foreign keys (CASCADE is the only action that can occur).

### ADR-0007: SQL semantic scope

- **Decision:** There is no NULL, and `NULL` is a reserved word that produces a syntax error. Keywords and identifiers are case-insensitive. The `WHERE` of `UPDATE` and `DELETE` accepts any `kBool` expression. An `ORDER BY` key is resolved as an integer position, an alias or a structurally identical expression, in that order, and must correspond to an item of the SELECT list. `COUNT` and `SUM` return zero on an empty set.

  `INT` is 64-bit, and `kRuntime` is returned with the message `numeric overflow` when INT overflows or a DOUBLE result is not finite. Expressions have static types, and `kBool` cannot appear in the SELECT list, in an assignment or in `DEFAULT`. A minus sign in operand position followed immediately by a numeric literal forms a negative literal, and otherwise parses as `0 - <operand>`.

  Column types accept aliases: `INTEGER` and `BIGINT` map to INT, `REAL` and `FLOAT` to DOUBLE, and `VARCHAR(n)` and `CHAR(n)` to TEXT with no length check. `NOT NULL` is accepted and has no effect. `INSERT` may omit a column that has a `DEFAULT` or is auto-increment, and `DEFAULT` is a constant expression evaluated at bind time.
- **Rationale:** Without NULL, comparison, aggregation, sorting and indexing need no three-valued logic. The header of an existing CSV can differ in case from the declared columns (the load accepts `ID,UserName,LOCATION` for `id,username,location`) while queries write names in any case, so identifiers have to be case-insensitive, as in SQLite. Resolving `ORDER BY` against the SELECT list keeps sorting above `ProjectNode`, so a plan has one structure. Signed integer overflow is undefined behavior in C++, and a non-finite DOUBLE prints as `inf` or `nan` and compares inconsistently, so both become errors. Static types let the Binder reject `WHERE id`. Every value is already non-NULL, so accepting the `NOT NULL` of imported DDL is correct.
- **Cost:** An empty-set `SUM` returns zero where standard SQL returns NULL, `ORDER BY` cannot reference a column outside the SELECT list, `-x` overflows when `x` is the minimum `int64_t`, and the length of `VARCHAR(n)` is not checked. In return the implementation and the test scope stay smaller.
- **Rejected:** Supporting NULL (three-valued logic touches every operator); a `WHERE` that accepts only `id = <constant>` (it deviates from standard SQL); wrapping around on overflow (the result is wrong and nothing reports it); checking `VARCHAR(n)` length (the catalog would record one more length and every `INSERT` and `UPDATE` would gain a check).

### ADR-0008: A multi-file write uses a staged commit to be all-or-nothing

- **Decision:** The write set of `Commit(CommitSet)` holds `catalog.csv` when it changes, the tables whose content changed and the tables to delete. `Commit` checks the write set and writes each changed file to `<file name>.temp`. When every write has succeeded, it renames each original file to `.orig` and each `.temp` file to the original name, one file at a time (a deleted table gets only the first rename), then removes the `.orig` files. If a step fails, files that already have an `.orig` are restored from it, leftover `.temp` files and newly created files are removed, and the engine returns `kIo`. The in-memory tables are replaced only after `Commit` succeeds (flow in Design Document 3.3).
- **Rationale:** A single `UPDATE visitors SET username = ...` rewrites three files (visitors, stories and reactions), and a partial write would leave the foreign key data inconsistent at the next load. `CREATE TABLE`, `ALTER TABLE` and `DROP TABLE` change `catalog.csv` and a data file together. Written separately, they can leave a catalog entry without its file, and the database then fails to open.
- **Cost:** Each commit costs two more renames and one delete. In return every file keeps its old content when a step fails.
- **Current state:** `fsync` is not called. A process terminated during the renames leaves `.orig` behind. The next load, `Commit` and `AppendRows` report `leftover <file>.orig`, and the user restores the files; the load refuses because the directory can hold old and new files side by side, or `catalog.csv.orig` without a `catalog.csv`, which would otherwise load as a database without tables. If a restoring rename fails, the error names the `.orig` file that holds the original content. `Commit` refuses a symbolic link at a `<file>.temp` path with `not a regular file: <file>.temp`, because writing the staged content would follow the link into another file; the check runs before the write, so a link created between the two is not caught. `AppendRows` bypasses the staged commit, so a process terminated midway leaves a half-appended row.
- **Rejected:** No rollback (the data-loss path above); a WAL in flatfile (it belongs to an engine with a different persistence format); routing `INSERT` through `Commit` (appending one row would become rewriting the whole file, which distorts the baseline's write cost).

### ADR-0009: The Binder produces plans with rule-based predicate pushdown and no cost estimation

- **Decision:** The Binder splits `WHERE` on `AND` and places each term at the lowest position where all of its columns are available (rules in Design Document 2.4). The join order follows the way `FROM` is written, chained left-deep.
- **Rationale:** With U rows in `depots` and E rows in `scans`, `WHERE d.id = 1` without pushdown filters after the join, so the join first produces about E merged rows. With pushdown only the matching `depots` rows enter it. Both are O(U + E); pushdown saves the merged rows and their memory.
- **Cost:** The plan shape depends on how `WHERE` is written, but no cost model or statistics are needed. Splitting on `AND` also changes short-circuit scope: a later conjunct may overflow on rows that an earlier one has already excluded.
- **Rejected:** No pushdown (temporary memory grows with E); a cost-based optimizer (it needs statistics and cost formulas).

### ADR-0010: SQL parsing uses a recursive-descent parser

- **Decision:** `SqlParser` handles SELECT, INSERT, UPDATE, DELETE, DDL and expressions with lexical analysis and a recursive-descent parser. Syntax outside the grammar in Design Document 2.3 returns a syntax error.
- **Rationale:** The project aims to accept standard SQL, whose clauses and expressions combine freely, and the port takes a general plan, so the parse result need not map to a fixed operation.
- **Cost:** The parser is larger and needs more tests. In return new syntax is added by adding grammar rules only.
- **Rejected:** Matching fixed statement shapes with regular expressions (it cannot accept every combination, for example different `WHERE` conditions).

### ADR-0011: Equality joins use a hash join

- **Decision:** `RunQuery` in `flat_file_executor.cpp` splits the `ON` condition of a `JoinNode` on `AND` and takes one condition of the form "one column of left equals one column of right" as the hash join key, building the hash table from the right input and probing it with the left. The other `ON` conditions and the predicate of the `FilterNode` directly above the join are residual conditions, evaluated before a combined row is written. Without an equality condition the join is a nested loop. The plan is a left-deep chain of `JoinNode`s that each pick their own key, so the plan does not depend on the number of tables, and a key may come from any table on the left. The parser accepts at most 64 `JOIN` clauses in one `SELECT` and reports `too many JOINs: at most 64 are allowed` at the 65th `JOIN` keyword.
- **Rationale:** With 10000 rows each in the tables of the volume data, a nested loop needs 10^8 comparisons and would overstate the join cost of the baseline, while a hash join is O(n + m). Filtering the residual conditions only after the join would let the number of temporary rows reach n · m. Running `SELECT COUNT(*) FROM depots d JOIN parcels p ON d.id < p.id WHERE d.id <= 400` on the volume data, imported into a flatfile database, on an Apple M4 under macOS 26.5.1 counted 3,919,800 rows and reached a peak resident set size of 1,498,284,032 bytes (measured 2026-11-20). The plan is a left-deep chain as deep as the number of joins, and the parser had no limit on it. On the same machine with a Release build (measured 2026-11-21), a `SELECT` that joins one table to itself 5,000 times finished in about 1 second, and one with 20,000 joins ran for 15 seconds and ended `strata_cli` with a segmentation fault (exit status 139). The cause was not examined with a debugger. The other long statements tried at 100,000 items (`OR`, `AND`, `+`, `||`, parentheses, select items, `INSERT` rows) either ran or returned a syntax error, so only the join count was unbounded. 64 is far above a query written by hand and far below the measured failure.
- **Cost:** The executor merges the join with the filter above it. In return memory is proportional only to the number of output rows, and `ON a = b AND c` is still O(n + m). A query that joins more than 64 tables is refused, and the limit is a constant in the parser (`kMaxJoins` in `sql_parser.cpp`).
- **Current state:** The parser accepts 64 joins and refuses 65 with the error above, at the offset of the 65th `JOIN` (UT-140). A statement with 100,000 joins is refused without building the clauses beyond 64.
- **Rejected:** Always a nested loop (10^8 comparisons overstate the baseline); sort-merge join (it sorts first, O(n log n)); no limit on the number of joins (20,000 joins crash the CLI, see Rationale); a limit in the Binder (the parser already holds the other input-size limits and refuses the statement before it builds the clauses).

### ADR-0012: The flatfile CSV format and storage limits

- **Decision:** CSV columns follow Request for Comments (RFC) 4180: a value with a comma or a double quote is wrapped in double quotes, and an embedded double quote is doubled. A TEXT value cannot contain `\r` or a newline, and storing one returns `kUnsupported`. The same applies to a TEXT `DEFAULT` in `CREATE TABLE` and `ALTER TABLE ADD COLUMN`, because `catalog.csv` stores it. A row whose only value is the empty string is written as `""`, since the loader skips a blank line. INT is 64-bit. `Commit` and `AppendRows` keep the line ending of the file's header line. The header stays as it is while the columns stay the same; `ALTER TABLE ADD COLUMN` and new files take it from the schema.
- **Rationale:** A newline is refused because the loader isolates errors line by line: a record that could span lines would let one unterminated quote swallow every row after it. An existing CSV file can use Carriage Return and Line Feed (CRLF, `\r\n`), as the volume data does, and the writers keep the line ending of the header line, so a value with `\r` or `\n` would mix endings.
- **Cost:** TEXT cannot hold a newline. That keeps a format error in one row from spreading.
- **Rejected:** Quoted fields that span lines (one unterminated quote would swallow the rest of the file); escaping newlines (not standard CSV, so other tools misread it); an error on any comma (users hit it with ordinary sentences).

### ADR-0013: Table definitions live in `catalog.csv` and change through DDL

- **Decision:** The schema lives in `catalog.csv` in the database directory, one row per column (format in Design Document 2.6). `CREATE TABLE`, `ALTER TABLE ADD COLUMN` and `DROP TABLE` are AST and plan nodes in the Domain, validated by the Binder and executed by the engine, which updates the catalog and the data file in one `Commit` (ADR-0008). The catalog, not the files in the directory, decides whether a table exists, and the table name `catalog` is reserved. Constraints are column-level only (`PRIMARY KEY`, `UNIQUE`, `NOT NULL`, `DEFAULT`, `REFERENCES`, `AUTOINCREMENT`), with single-column primary and foreign keys. A referenced column must be a primary key or `UNIQUE`. `ADD COLUMN` must carry `DEFAULT` and cannot carry `PRIMARY KEY`, `UNIQUE`, `REFERENCES` or `AUTOINCREMENT`. `DROP TABLE` is rejected while another table references the table.
- **Rationale:** A CSV header holds only column names, so types and keys need a home elsewhere. Without a catalog, types would be guesses (is `00123` an INT or TEXT?) and a stray file would become a table. Storing the original DDL text, as SQLite does, would put the parser in the load path and make the Infrastructure depend on the Adapter. `ADD COLUMN` takes no constraints because each would mean rechecking every old row.
- **Cost:** The catalog is one more file, table files are named `<table name>.csv` in lowercase, and there are no composite keys or table-level constraints. The schema becomes data, and both engines share one DDL front end.
- **Current state:** A directory of bare CSV files has no `catalog.csv`. After its files are adopted with `CREATE TABLE` statements (ADR-0014), `.open` of the directory works; ET-18 does it for the four tables of `sample_my_db/`.
- **Rejected:** A header with types such as `id:INT` (no longer an ordinary CSV, and keys still cannot be expressed); the schema as JavaScript Object Notation (JSON) (needs a parser or a new dependency); inferring types at `.open` (guesses); the original DDL text in the catalog (the Infrastructure would depend on the parser).

### ADR-0014: `CREATE TABLE` adopts an existing CSV

- **Decision:** When `CREATE TABLE` runs and the table's CSV already exists, the statement checks the header and parses the rows with the load rules. If the remaining rows satisfy the declared primary key, `UNIQUE` and foreign keys, the CSV stays untouched, only the catalog is written, and the rows are loaded. A violation or a header mismatch reports an error and creates no table. A 0-byte file counts as 0 rows, and the output states the number of rows adopted. Only `CREATE TABLE` adopts. `.import`, and a `CREATE TABLE` that found no file, write a new file and fail with `kIo` when a file already exists at that path (Design Document 2.7, 2.9).
- **Rationale:** A user often has the CSV files already, and attaching them beats moving them away and importing the rows with `INSERT`. The declared constraints have to hold, because later RESTRICT, cascade and uniqueness checks rest on them. Unparsable rows are rejected under the load rules, so the three problem lines of the `students.csv` in ET-18 do not block adoption.
- **Cost:** Rows rejected at adoption disappear from the file at the next rewrite, as at load (ADR-0004). Existing data needs no conversion.
- **Rejected:** Always reporting "file already exists" (the user must move the file first); overwriting the CSV (data loss); skipping validation (the declared constraints might not hold).

### ADR-0015: The database directory is protected by `flock`

- **Decision:** At `.open`, `DirectoryLock::Acquire` takes an exclusive `flock` (`LOCK_EX | LOCK_NB`) on the dedicated file `.strata.lock` in the database directory. If another process holds it, `.open` fails and the current connection stays. `OpenedDatabase` holds the lock as a `std::shared_ptr<void>`, and reopening the same directory in the same process reuses it. When the directory is not writable (creating the lock file returns `EACCES` or `EROFS`), no lock is taken, and a later reopen of that directory calls `Acquire` again instead of reusing the empty lock.
- **Rationale:** Two processes that `.open` the same directory and then write lose data silently: the later writer rewrites the whole file from its own memory. The lock cannot sit on `catalog.csv`, because the staged commit replaces that file by rename and a lock on the old inode protects nothing. An `flock` lock belongs to each `open()`, so a process locking the same directory twice would block on itself, hence the reuse on reopen. The kernel drops the lock when the process exits or crashes, which a Process Identifier (PID) file cannot do.
- **Cost:** Only one process can open a database at a time, even one that only queries. The lock is advisory, so it cannot stop a text editor, and `flock` behaves differently on network file systems. In return a second writer gets an explicit error instead of silently overwriting the first.
- **Current state:** When the lock is held, the output is `error: could not open <directory>: database is locked by another process`.
- **Rejected:** A shared lock for readers (at `.open` it is not known whether the connection will write); a PID file (left behind after a crash); a lock on `catalog.csv` (the rename defeats it); no protection (writes are lost silently).

### ADR-0016: Auto-increment takes the current maximum plus 1

- **Decision:** For a column declared `INTEGER PRIMARY KEY AUTOINCREMENT`, an `INSERT` that omits it takes the greater of the column's current maximum and 0, plus 1, so an empty table or one with only negative values gives 1. The engine fills the value in during `PlanMutation`, because the Binder is a pure function that reads no data and only marks `InsertNode::generated_index`. An explicit value is used as given. At the `int64_t` maximum the engine reports `kRuntime` with the message `numeric overflow`. `RETURNING` is not provided.
- **Rationale:** Taking the maximum needs no extra state, so an `INSERT` stays a single-file append instead of also rewriting `catalog.csv`. A value freed by deleting the largest row is reused, which causes no dangling reference because a referenced row cannot be deleted (ADR-0002).
- **Cost:** An id can be reused after the largest row is deleted, which the `AUTOINCREMENT` of SQLite prevents, and each `INSERT` that omits the id scans the table once, O(n). There is no persistent counter to maintain.
- **Rejected:** Recording the next value in `catalog.csv` (every `INSERT` would become a two-file commit); filling the value in the Binder (it cannot read data).

### ADR-0017: The CLI ends a statement with `;`, and a statement may span lines

- **Decision:** The Command-Line Interface (CLI) accumulates input lines and ends a statement at a `;` outside a string literal. A statement may span lines, a line may hold several statements, and a lone `;` is skipped. If the input ends before the statement does, the output is `error: incomplete statement at end of input`. A command that starts with `.` is recognized only when no statement is in progress, and it takes the whole line. The exception is a line containing only `.cancel`, which discards the accumulated text when a statement is in progress outside a string literal (ADR-0023).
- **Rationale:** A longer `CREATE TABLE` needs line breaks, and `.schema` output (ADR-0018) is multi-line already. A `;` terminator is the convention of sqlite3 and psql, and without one the CLI cannot tell an unfinished statement from a one-line one. A string literal can contain `;` and newlines, so the splitting tracks whether it is inside one.
- **Cost:** A statement without a trailing `;` waits for one instead of running, which is what lets a statement span lines.
- **Rejected:** One statement per line (a long DDL cannot be broken, and `.schema` output could not be run again); a blank line as terminator (it is legal content inside a literal); a trailing `\` for continuation (not an SQL convention, and legal inside a literal).

### ADR-0018: `.schema` prints re-executable `CREATE TABLE` statements

- **Decision:** `.schema [<table>]` prints `CREATE TABLE` statements in catalog order, one column per line, each ending with `;`. The output can be fed back to the CLI and recreates the same schema in an empty database. Types are written as the standard `INT`, `DOUBLE` and `TEXT`, and `NOT NULL` is not printed. `FormatCreateTable` in the Adapter produces the text, and the Application returns only `TableSchema`.
- **Rationale:** Users want to see a table's columns and constraints and to move a schema to another directory, and printing DDL does both with no second format or parser. Referenced tables come first in the catalog, so foreign key targets exist when the output runs again. Without NULL, `NOT NULL` has no effect, so omitting it changes nothing.
- **Cost:** The Adapter holds a second textual form of DDL that has to match the parser's grammar; a round-trip test guards that. The gain is a schema that can be carried to another directory and rebuilt.
- **Rejected:** A column list in table form (it cannot be executed again); DDL text returned by the Application (the text format is presentation); the original DDL text in the catalog (see ADR-0013).

### ADR-0019: Syntax and semantics of operators, functions and `LIMIT`

- **Decision:** `*`, `/`, `||` and `LIKE` are binary operators. Precedence from lowest to highest is `OR`, `AND`, comparison and `LIKE`, `+ -`, `* /`, `||`, then unary minus and parentheses, and `LIKE` does not chain. `/` between two INT values truncates toward 0, and mixed operands use DOUBLE division. A divisor of 0 reports `kRuntime` `division by zero`, and dividing the minimum INT by `-1` reports `numeric overflow`. `||` accepts only TEXT. A `LIKE` pattern has `%` and `_` and no `ESCAPE`; `_` matches one 8-bit Unicode Transformation Format (UTF-8) character, and American Standard Code for Information Interchange (ASCII) letters match case-insensitively.

  The scalar functions are `LOWER`, `UPPER`, `LENGTH`, `SUBSTR`, `TRIM`, `ABS`, `ROUND` and `CAST(<expr> AS <type>)`, and the aggregates of this decision are `AVG`, `MIN` and `MAX`. Functions and these aggregates are recognized by a name immediately followed by `(` and are not reserved words, while `LIKE`, `LIMIT` and `OFFSET` are. `AVG` returns DOUBLE, and `MIN` and `MAX` return the type of their argument. Without `GROUP BY`, `AVG`, `MIN` and `MAX` over no rows report `kRuntime` `<FN> over no rows`. `ROUND` rounds half away from zero on the binary value the DOUBLE stores, and the result is the DOUBLE nearest to the decimal value.

  A `SELECT` may end with `LIMIT <n> [OFFSET <n>]`, where `<n>` is a non-negative integer literal, and `LimitNode` sits above `SortNode`.
- **Rationale:** The precedence is SQLite's, so an expression brought over from SQLite keeps its meaning. Integer division truncates toward 0 as in C++, PostgreSQL and SQLite, and without NULL a division by 0 can only be an error. Implicit conversion would make `'id=' || 5` depend on a number format, so conversion goes through `CAST`. Without `ESCAPE` every byte of a pattern has one meaning, and the `LIKE` of SQLite is also ASCII case-insensitive. `min`, `max` and `length` are common column names, and recognizing functions by the following `(` keeps those names usable for columns. `CASE` and date functions are out of scope. `ROUND` follows the stored binary value because of cases like `round(2.675, 2)`. On an Apple M4 (measured in C++ on 2026-11-11), `2.675 * 100` rounds to `267.5`, so `std::round` on the product gives `268` (`2.68`). The binary value of 2.675 is `2.67499999999999982236431605997495353221893310546875`, slightly below half, and `std::fma(2.675, 100.0, -267.5)` is `-1.7763568394002505e-14`. The rounding error of the product that `fma` recovers tells "exactly half" from "slightly below half", and sqlite3 3.51.0 returns `2.67` for the same call.
- **Cost:** `LIKE`, `LIMIT` and `OFFSET` cannot be identifiers, and a negative `SUBSTR` start does not count from the end as it does in SQLite. The rules themselves follow from the binary value and the position, with no exceptions to remember.
- **Current state:** Tests cover the precedence of `||` and `*`, the O(n · m) matching of `LIKE`, the argument checks of functions, each runtime error message (Design Document 2.3) and the parse errors of `LIMIT`. The behaviors that differ from sqlite3 on purpose are a negative `SUBSTR` start, `AVG`, `MIN` and `MAX` of an empty set, and division by 0.
- **Rejected:** `CASE` and date functions (new nodes in the Binder and evaluation, and no date type); implicit conversion between TEXT and numbers (the result depends on the format and conflicts with the type rules of `kBind`); `ESCAPE` for `LIKE` (a pattern byte would no longer have one fixed meaning); `LIMIT` accepting expressions (the Binder would need constant evaluation and type checking).

### ADR-0020: A multi-row `INSERT` is all-or-nothing through a single append

- **Decision:** `INSERT ... VALUES (...), (...)` produces one `InsertNode` with several `rows`. `PlanMutation` checks the rows in order and reports the first violation, and a failed statement changes nothing. A duplicate primary key or `UNIQUE` value is checked against the existing rows and the earlier rows of the same statement, a foreign key against the existing tables only. Auto-increment values increase in row order. `IFlatFileRepository::AppendRows` appends all the rows with one write and truncates the file back to its pre-append size on failure.
- **Rationale:** With `AppendRow` called once per row, a failure at row k leaves the first k - 1 rows in the file. One write also opens the file and checks its header once for N rows. Two rows of one statement can carry the same primary key, which a check against the existing rows alone cannot see.
- **Cost:** The primary key and `UNIQUE` check of `PlanInsert` builds a hash set of the existing values, O(n) for n rows, so an N-row check takes O(n + N) instead of O(n · N). A process terminated midway through the write can still leave a partial row (Design Document 2.15).
- **Current state:** For multiple rows, the Binder prefixes its error messages with `row <k>: `.
- **Rejected:** `AppendRow` row by row (not atomic); one `Commit` that rewrites the whole table (it rewrites an O(n) file only to append); `INSERT ... SELECT` (out of scope).

### ADR-0021: `.import` loads an external CSV and infers types from the data

- **Decision:** `.import <file.csv> [<table>] [--pk <column>] [--type <column>=<type>]... [--skip-bad-rows]` imports an external CSV as a new table. `Cli` parses the arguments, and `QueryService::ImportCsv` reads the source through the Domain's `ICsvSource` (implemented in the Infrastructure by `FileCsvSource`), runs the pure function `InferImport` and hands an `ImportTableNode` to the engine, which writes it in one staged commit. A column is inferred as INT or DOUBLE only when writing the parsed value back reproduces the cell exactly, and as TEXT otherwise. The default is strict, so one bad row fails the import; `--skip-bad-rows` skips and reports bad rows, and `--type` sets a type explicitly. A duplicate primary key is always an error. Table and column names cannot be reserved words. The import only creates `<table>.csv`: when a file of that name already exists in the database directory, the import fails and leaves it alone, even when it is the source file itself. The rules are in Design Document 2.7.
- **Rationale:** Adopting an existing CSV means hand-writing a matching `CREATE TABLE`, the biggest barrier for a new user. A written table is rewritten in the standard format, so if inference treated `007` as INT, the next `UPDATE` would turn `007` into `7` in a column the statement never touched. The exact round-trip rule makes the import change no byte. Load rejects bad rows and reports them because the file already exists; at import the user can still fix the source, so the default is to fail. The `students.csv` of ET-38 has three bad rows (the `id` on line 12 is `x1010`, and lines 17 and 18 have 4 and 6 fields where the table has 5), so if every row took part in inference, `id` would become TEXT and `WHERE id = 1001` would be a type error.
- **Cost:** A CSV with bad rows, such as that `students.csv`, cannot be imported with one command and no options, `UNIQUE` and foreign keys are not inferred (a CSV that needs them is adopted with `CREATE TABLE`), and quoted fields with newlines are not supported. The import never changes the user's data or drops it silently.
- **Current state:** `courses.csv` and `enrollments.csv` of `sample_my_db/` import 12 and 144 rows with one `.import` each (ET-37). The `students.csv` of ET-38 by default reports `line 17: expected 5 fields, found 4`, and with `--pk id --type id=INT --skip-bad-rows` it imports 30 rows and skips 3. XE-01 imports the volume data into both engines: `depots.csv` imports 10000 rows and skips the 3 lines of VU-06, and `parcels.csv` and `scans.csv` import 10000 rows each.
- **Rejected:** Inferring types by majority vote (the threshold is arbitrary, and data is dropped quietly); all columns as TEXT (what the `.import` of SQLite does, and every later numeric comparison would need a `CAST`); modifying the source file (it is the user's data); the CLI reading the file and inferring directly (the CLI only calls Application operations).

### ADR-0022: External modification is detected by file size and modification time

- **Decision:** `CsvRepository` records the size and modification time of `catalog.csv` and of each table file at load; a file that does not exist is recorded too. A successful `InspectTable` records the file it inspects, so a CSV adopted by `CREATE TABLE` (ADR-0014) is covered as well. A write that must create a new file checks that the file does not exist instead of comparing a record. Before writing, `Commit` and `AppendRows` compare every file they will write or delete against the record. On a difference they return `<file name> changed on disk since it was loaded; run .open again` and write nothing. The record of a load or an inspection is taken before the file is read, so a change made during the read is caught. After its own successful write, and after an append that failed and was truncated back, the repository updates the record.
- **Rationale:** If a CSV is edited while the CLI is open, the next write statement rewrites the whole table from the old in-memory data and silently overwrites the edit. Measured on 2026-11-11: after one row was appended to `students.csv`, `UPDATE` returned the file to its original 31 lines with no message. `flock` is advisory and cannot stop an editor (ADR-0015). The check costs one `stat` per written file.
- **Cost:** An external change that keeps both size and modification time goes undetected. A rejected write means running `.open` again, which loses nothing because writes are immediate. In return external edits are not overwritten silently.
- **Current state:** After a file is modified following the load, `UPDATE`, `INSERT` or DDL returns `kIo`, the file keeps the external content, and memory is unchanged. A change in size only, or in modification time only, is detected too. The repository's own consecutive writes are not misjudged, and `.open` again recovers the state.
- **Rejected:** Merging at write time (it needs a three-way merge, and the only row identity is the primary key); content hashing (every write would read the whole file once more); a file lock (advisory); silent reload (the user's statement would run on data the user does not know about).

### ADR-0023: CLI input tolerance rules

- **Decision:** `--` to the end of the line starts a comment, and `StatementBuffer` and the lexer ignore `;` and single quotes inside it. U+00A0, U+3000 and U+2000 to U+200A count as whitespace. A full-width semicolon `；` outside string literals and comments prints `error: full-width ';' (U+FF1B) found; use ASCII ';'` and discards the line. Other unexpected characters are described by code point (`U+2019`). While a statement is in progress and the input is outside a string literal, a line containing only `.cancel` discards the accumulated text. When no statement is in progress and a line starts with a command name without the `.`, the CLI prints `error: commands start with '.'; did you mean .<name>` and discards the line. When no statement is in progress and a line starts with `.` but is not a command, the CLI prints `error: unknown command .<name>; .help lists the commands` and discards the line. While the input is inside a string literal, the continuation prompt is `     '> ` (5 spaces, then `'> `). `.clear` clears the screen in interactive mode.
- **Rationale:** Scripts and pasted SQL often carry comments. A Chinese input method in full-width mode produces full-width spaces and semicolons, and curly quotes come from copied documents. These characters are invisible or look like ASCII, so the user sees only that nothing happens. Without the missing-dot rule, `open mydb` would start a statement and stop at the continuation prompt, with `;` or quitting as the only way out, because commands are recognized only when no statement is in progress (ADR-0017). An unknown `.tbles` had the same effect: the line started a statement that ran up to the next `;`, so in `.tbles`, `INSERT INTO t VALUES (1);` the `INSERT` was swallowed into one syntax error and the row was never written (reproduced 2026-11-21). No SQL statement starts with `.`, so the line can be refused at once. `.cancel` is recognized only outside a string literal, because lines inside a literal are data. Ctrl-L does nothing in a terminal without line editing, hence `.clear`.
- **Cost:** `SELECT 1--2` changes meaning from "1 minus -2" to a comment, as in SQLite. A full-width semicolon makes the user retype the line, since accepting it would let input method behavior shape the grammar. A string literal left open is closed only by the closing quote or Ctrl-C. In return each of these "no output" cases gets a message or a way out.
- **Current state:** Each rule has a string-stream test (the unknown `.` line is IT-156). The command names recognized when the `.` is missing are `open`, `engine`, `import`, `tables`, `schema`, `dump`, `help`, `quit`, `exit`, `clear` and `cancel`.
- **Rejected:** Running a command name without `.` directly as a command (a mistyped `open` or similar would run as a command, MySQL style); accepting the full-width semicolon as `;` (it silently extends the grammar); `/* */` comments (they need lexer state across lines); a built-in pager and line editing (they add a dependency).

### ADR-0024: A paged database is one file in the directory, with the catalog stored in system tables

- **Decision:** `paged.db` in the database directory holds all data of the paged engine. Page 0 is the file header, and pages 1 and 2 are the first pages of the two system tables, `sys_tables` and `sys_columns`. The pages of the user tables and the system tables follow. Page numbers form one numbering space across the whole file.
- **Rationale:** The buffer pool and the planned WAL address a page by one page id and need no (file, page) pair. The catalog and the data use the same page, table heap and buffer pool mechanisms, so no second format is needed and the planned WAL protects both. Persistence has only one file to `Sync`. See Design Document 2.6 and 2.10.
- **Cost:** The pages of several tables are interleaved in the file, so the pages of one table are not contiguous in a scan. The file never shrinks: dropping a table puts its pages on a free list for reuse and does not return them to the file system (ADR-0046). In return the file has a single page id space and a single synchronization target.
- **Current state:** A new database file is 12288 bytes (three pages). The three tables of the volume data hold 30000 rows in total and occupy 549 heap pages (`depots` 80, `parcels` 312 and `scans` 157) and, with the index of each primary key, 207 index pages. `paged.db` is then 3,108,864 bytes, which is 759 pages including the 3 fixed pages. The heap pages were measured on 2026-11-20 on an Apple M4 and the index pages and the file size on 2026-11-24 on macOS (Darwin 25.5.0), both with a Release build; before the indexes the file was 2,260,992 bytes, which is 552 pages.
- **Rejected:** One file per table plus a separate catalog file (a page id would carry a file number, the WAL would record the file number, several files would need synchronizing and the catalog would need another format); the catalog stored as a CSV or text side file (it bypasses the buffer pool and is not protected by the WAL).

### ADR-0025: A page is 4096 bytes with a common header holding a CRC-32C and an LSN, in fixed-width little-endian

- **Decision:** `kPageSize` is 4096. Every page starts with a 32-byte common header with the fields `checksum`, `page_id`, `page_type`, `slot_count`, `free_end`, `dead_bytes`, `next_page_id`, `table_id` and `lsn`. `checksum` is a Cyclic Redundancy Check (CRC) of the kind CRC-32C over the remaining bytes from offset 4, and `lsn` is the Log Sequence Number (LSN). Multi-byte integers are read and written byte by byte, little-endian and fixed-width. The CRC is sealed before a page is written out, and the CRC and `page_id` are verified after a page is read in.
- **Rationale:** (1) The page size is not larger than an operating system page and divides it evenly. The operating system page is 4096 bytes on x86 and Linux, and 16384 bytes on macOS (measured on 2026-11-11 with `sysctl hw.pagesize` on the development machine, an Apple M4). When frames and file offsets are aligned to 4096, the I/O of one page does not cross an operating system page. (2) The rows of the volume data are small. Measured on 2026-11-20 on its three tables, the largest column content of a single row is 119 bytes (`parcels`), and the largest encoded row is 146 bytes. A page therefore holds at least 27 rows, and the tuple cap of 4060 bytes is far larger than needed. (3) Until the planned WAL exists, the CRC is the only means to detect corrupt pages and interrupted writes (torn pages), and `page_id` detects a write to the wrong location. (4) `lsn` is reserved as 0 for now, so adding the WAL later does not change the format. (5) Byte-by-byte little-endian reads and writes make the file independent of the host byte order and of compiler alignment and padding. See Design Document 2.10.
- **Cost:** Each page gives up 12 bytes of its header to `checksum` and `lsn`, and every page read in or written out costs one CRC computation. In return corrupt pages are detected and the format does not need a revision for the WAL. The time cost of the CRC is not measured yet.
- **Current state:** The CRC-32C of `"123456789"` is `0xE3069283` (the RFC 3720 polynomial). For a page that holds data, with one bit flipped in each of the 4096 bytes, `VerifyHeader` detects all the flips as `kCorrupt`.
- **Rejected:** An 8192-byte page (the data volume is small, the frame count would halve and no measurement supports it); no checksum (until the WAL exists there is no other means to detect corrupt pages); adding `lsn` when the WAL is built (a format revision); reading and writing the header through a struct directly (the file would vary with the host byte order and the compiler alignment).

### ADR-0026: Slot numbers are stable, a RID may be reused after deletion, and an update does not cross pages

- **Decision:** A `Rid` is a page id plus a slot id. `Delete` marks the slot as dead by setting `offset` and `length` to 0, and the next `Insert` first reuses the dead slot with the lowest number. Compaction moves the live tuples to the end of the page and removes the contiguous dead slots at the tail. It does not change the number of any live slot. `Update` does not cross pages. If the new tuple fits in the same page, the original `Rid` is kept. If it does not fit, `kNoSpace` is returned and the caller runs `Delete` and then `Insert`.
- **Rationale:** Stable slot numbers make compaction move only bytes, so a holder of a `Rid`, such as the planned index, does not need to update anything on compaction. Reusing dead slots keeps the slot array from only growing. Moving a tuple across pages changes its `Rid`. That decision belongs to the execution layer and the index together, so the paged layer does not make it in advance. See Design Document 2.11.
- **Cost:** A `Rid` may point to different rows before and after a deletion, so a holder must remove its entry when the row is deleted. A longer new tuple that does not fit in the same page gets a new `Rid`. In return compaction and in-place updates do not affect the `Rid`.
- **Current state:** After a deletion, the next insert in the same page returns the lowest previously dead slot number. 20000 random operations (insert, delete, update, get, scan) agree with a `std::map<Rid, Row>` reference, for each of the two replacement policies, with three seeds.
- **Rejected:** No slot reuse (the slot array only grows and each dead slot occupies 4 bytes forever); a forwarding pointer for cross-page updates (a read needs an extra hop, the format is more complex and the execution layer has no need for it); renumbering slots on compaction (every `Rid` holder would need an update).

### ADR-0027: A tuple is encoded in schema column order, capped at 4060 bytes, with no overflow

- **Decision:** `TupleCodec` encodes a row column by column in the order of `TableSchema::columns`. INT takes 8 bytes little-endian, DOUBLE takes the 8-byte IEEE 754 bit pattern, and TEXT takes a 2-byte length plus the content. A tuple stores no column count, type or NULL bitmap. A tuple is at most 4060 bytes, and a page then holds only that one tuple. A larger tuple returns `kTooLarge`.
- **Rationale:** The system has no NULL, so a tuple needs no NULL bitmap. The schema comes from the catalog, so a tuple does not repeat the column types, and the bytes saved per row let a page hold more rows. Encoding in column order makes decoding a single pass. The largest row of the volume data is 146 bytes (ADR-0025), and an overflow page would need a new page type, links and deletion rules, with no demand for it. See Design Document 2.10.
- **Cost:** Old tuples cannot be decoded after a schema change, so `ALTER TABLE ADD COLUMN` rewrites the table into a new page chain (ADR-0045). A value larger than one page cannot be stored. In return a tuple carries no extra metadata per row.
- **Current state:** `DOUBLE` is copied bitwise, and the bits of `-0.0` and `NaN` round-trip unchanged. A tuple of 4060 bytes in total succeeds, and one of 4061 bytes returns `kTooLarge`.
- **Rejected:** A type tag per column (one extra byte per row times the column count); a column offset array (it serves the read of a single column only, while all current access decodes the whole row); an overflow page (no demand).

### ADR-0028: The buffer pool synchronizes with one pool mutex and one latch per frame

- **Decision:** `BufferManager` protects the page table, the frame metadata, the free list, the replacement policy and the counters with one `std::mutex`, called the pool mutex. Each frame has one `std::shared_mutex` that protects the page content. A pin and a latch are held only by the RAII `PageGuard`, whose destructor releases the latch first and then the pin. The pool mutex is not held while waiting for a latch. On a miss, writing back the dirty victim page and reading in the new page run inside the pool mutex. When no frame can be replaced, `kNoFrame` is returned and the call does not wait.
- **Rationale:** This design prevents a data race on the page table and the metadata, a lost update of the dirty flag and the pin, and a deadlock. The lock order is latch first and pool mutex second, and a holder of the pool mutex waits for no latch, because the replaced frame has no pin. Doing the I/O inside the mutex gives "write back the victim page" and "another thread reads in the same page" a definite order, so no per-frame I/O state or set of write-backs in progress is needed. The RAII guard releases the pin on every path, including early returns and errors. See Design Document 2.12.
- **Cost:** Misses are serialized. During a disk I/O every other `FetchPage` waits for the pool mutex, a hit included. In return the implementation needs no frame state machine and the lock order can be reasoned about. The cost of serializing misses is not measured yet. It is to be measured before deciding whether to move the I/O out of the mutex.
- **Current state:** `hits + misses` equals the number of `FetchPage` calls, failed calls included. After each of the error paths (read, write back, allocation, sync and corrupt page), `PinnedFrameCount()` is 0. ThreadSanitizer reports nothing when 8 threads scan data larger than the pool at the same time, and when one writer and 4 readers access the same table at the same time.
- **Rejected:** Moving the I/O out of the pool mutex and coordinating with a frame load state plus a condition variable (the correctness cost is high and no measurement shows a need); locking per page table bucket (the concurrency scope is many readers and a single writer, with no demand); waiting for a latch inside the pool mutex (it deadlocks with a thread that holds a latch and then needs the pool mutex).

### ADR-0029: The replacement policy is an interface, implemented as LRU and simplified 2Q

- **Decision:** `IReplacementPolicy` is a state machine without locks, with the operations `RecordLoad`, `RecordAccess`, `SetEvictable`, `Evict` and `Remove`. `BufferManager` calls it inside the pool mutex. Two policies are implemented: `LruPolicy`, for Least Recently Used (LRU), and a simplified `TwoQPolicy`. In `TwoQPolicy` the A1in target is 1/4 of the capacity, A1out keeps 1/2 of the capacity in page ids, and a frame in A1in does not move when it is accessed again. `BufferManager` selects the policy through `ReplacementPolicyKind`, and the default is `kLru`.
- **Rationale:** The project compares the hits and misses of the two policies on the same access sequence, so both are implemented and can be switched. 2Q lets the pages loaded by a one-off sequential scan enter only A1in, so they do not push out the repeatedly used pages in Am. LRU has no such protection. The policy contains no lock and no I/O, so fixed operation sequences are enough to verify it. See Design Document 2.12.
- **Cost:** `TwoQPolicy::Evict` takes O(N) at worst when many frames are pinned, where N is the number of frames, and the simplified version has no adaptive A1in size. In return two policies can be compared side by side and the implementation stays simple.
- **Current state:** Given the same access sequence under both policies (capacity 8, a hot set of 4 pages, 8 filler pages and 40 one-off scan pages), the last round over the hot set has 4 misses with LRU and 0 with 2Q. The same file opened with 16 frames under each policy, repeating the sequence "scan H, F, G, H, B, H" (page counts 4, 12, 4, 60), has 4 misses with LRU and 0 with 2Q in the last scan of H (measured once on 2026-11-12). The rows of each scan are the same under both policies.
- **Rejected:** LRU only (there is nothing to compare against); Clock, LRU-K and ARC (outside the current scope; no other rejection reason is recorded).

### ADR-0030: Disk I/O is isolated behind `IPageStore`

- **Decision:** `IPageStore` is an interface owned by the paged layer. Its operations are `ReadPage`, `WritePage`, `AllocatePage`, `PageCount` and `Sync`, and all of them work in units of whole pages. `FilePageStore` implements it with the POSIX calls `pread`, `pwrite` and `fsync`, and `Sync` uses `F_FULLFSYNC` on Apple platforms. `MemoryPageStore` implements it with an in-memory page array that can inject read, write, allocation and sync failures.
- **Rationale:** Read, write, allocation and sync failures cannot be reproduced reliably on a real file. The error paths of `BufferManager`, `TableHeap` and `Catalog` (no leaked pin, no lost dirty page, undo of table creation) need failures injected deterministically. Unit tests need no file. A second implementation, `MemoryPageStore`, already exists, so the interface has a reason to exist. See Design Document 2.2 and 2.15.
- **Cost:** The paged layer carries one more interface and one implementation that only tests use. In return the error paths are verified deterministically.
- **Current state:** `Sync` of `FilePageStore` calls `fcntl(F_FULLFSYNC)` first on Apple platforms and falls back to `fsync` on failure. `MemoryPageStore` can fail the n-th read, write, allocation or sync counted from now, which is how error propagation and the absence of leaked pins are verified. Whether `F_FULLFSYNC` and `fsync` flush the data out of the storage device cache cannot be observed inside the process, and there is no test.
- **Rejected:** Calling POSIX functions directly (failures cannot be injected); a mock framework (the project has no external test framework).

### ADR-0031: The free-space map of a table heap exists only in memory

- **Decision:** Opening a `TableHeap` walks the whole page chain, reads the header of each page and rebuilds the chain tail and the in-memory free-space map. The map is a `std::set` ordered by capacity plus a `std::unordered_map` from page id to capacity. The free-space map is not written to the file.
- **Rationale:** A persisted free-space map would be another kind of page, and its updates must stay consistent with the updates of the data pages. There is no cross-page atomicity until the planned WAL exists. The volume data is 30,000 rows on about 550 pages, so the rebuild reads only about 550 headers. See Design Document 2.11.
- **Cost:** Opening each table costs O(P) page reads, where P is the number of pages. In return the format stays simple and there is no second copy of data to keep consistent.
- **Current state:** Opening twice gives the same free-space map, and the map equals the one maintained step by step over 500 random inserts and deletes. The three tables of the volume data have 549 heap pages in total. Opening the three tables, which rebuilds the free-space map, takes about 5.3 milliseconds in total. Measured on 2026-11-20 on an Apple M4 with a Release build and 64 frames, as the median of 7 opens.
- **Rejected:** A persisted free-space map page (updates must be consistent with the data pages, and there is no atomicity until the WAL exists); a directory page recording the remaining space of each page (same reason); walking the whole chain on every `Insert` to find space, which costs O(P).

### ADR-0032: The catalog is cached on read, and table creation has no transaction protection

- **Decision:** `Catalog::Load` walks the two system tables, validates them and builds an in-memory cache. The cache is a vector of schemas plus a `std::unordered_map` keyed by lowercase name. `FindTable` and `TableNames` read only the cache, and a `std::shared_mutex` protects it. `CreateTable` runs these steps in order: it checks that each of the schema's system table rows fits in one tuple, allocates the first page of the table, inserts one row into `sys_tables` and the column rows into `sys_columns`, and updates `next_table_id` in the file header. When a step fails, the system table rows already inserted are deleted on a best-effort basis, and when the undo also fails, the error message reports both failures. The cache is updated only on success. `Load` also verifies that `next_table_id` in the file header is greater than every `table_id`, so a leftover of "row inserted but `next_table_id` not yet updated" is detected, and the number is not reused at the next table creation. The name of a user table cannot start with `sys_`.
- **Rationale:** The Binder calls `FindTable` for every statement. Scanning the system tables each time costs O(T × C) decodes, where T is the number of tables and C is the number of columns per table, and the cache makes it O(1) plus one copy. The system tables use `TableHeap`, so the planned WAL protects them together with the data. Until then there is no transaction, and best-effort undo plus the validation in `Load` is the largest protection available. See Design Document 2.6 and 3.4.
- **Cost:** Table creation that terminates midway leaves pages and rows behind. `Load` detects them and returns `kCorrupt`, and there is no repair. In return the paged layer needs no transaction mechanism for now.
- **Current state:** After a failed `CreateTable`, with a failure injected at the second allocation, reopening the database succeeds and no system table row is left. After the injection is cancelled, the same `CreateTable` succeeds. A schema with a system table row longer than 4060 bytes is refused with `kInvalidArgument` and leaves the page count unchanged. `Load` returns `kCorrupt` for each of 17 kinds of inconsistent system tables and file headers, five of them foreign keys whose target is missing or does not match, and the message names the table or column.
- **Rejected:** Serializing the whole catalog into one page blob (the number of tables and columns would be limited by a single page); scanning the system tables on every `FindTable`; no undo when `CreateTable` fails (a single I/O failure would make the database impossible to open).

### ADR-0033: The engine is named `paged`

- **Decision:** The second storage engine is called `paged`. The name is used in the directories `include/strata/paged/` and `src/paged/`, in the namespace `strata::paged`, in the argument of `.engine flatfile|paged` and in the documents.
- **Rationale:** The name describes the mechanism, storage in units of pages, and is symmetric with `flatfile`, so the difference between the two engines shows in the names. The name appears in every file path and namespace, and deferring the decision would make a later rename cover all of the paged code.
- **Cost:** The name `paged` does not point to a specific implementation. The engine is still called `paged` if the page organization is replaced later. In return the names of the two engines each describe their storage mechanism.
- **Current state:** The directories `include/strata/paged/` and `src/paged/` and the namespace `strata::paged` exist. The type names inside `paged` carry no engine name (ADR-0035), so a rename affects the namespace, the directories, the argument of `.engine`, the `test_paged_` prefix of test function names and the prefixes of test IDs (`PU-`, `PI-`, `PE-`, `XU-`, `XI-`, `XE-`).
- **Rejected:** A product-style code name (the name does not show the storage mechanism); `page` (too short and confusable with a common noun).

### ADR-0034: Each frame latch occupies one cache line

- **Decision:** Each frame latch (`std::shared_mutex`) of `BufferManager` is aligned with `alignas(kCacheLineSize)`, and `kCacheLineSize` is 128. The latch array is allocated with the C++17 over-aligned `operator new`. The latch addresses of adjacent frames differ by at least 128 bytes. The frame metadata (`page_id`, `pin_count`, `is_dirty`) is not aligned, is packed tightly and is protected by the pool mutex.
- **Rationale:** Readers update the internal state of a latch with atomic operations outside the pool mutex. When the latches of adjacent frames share one cache line, threads that take the latches of different frames invalidate each other's cache lines. This is false sharing. It reduces the scalability of concurrent reads, and it is not visible in the code but appears only in measurement. The cache line of the development machine, an Apple M4, is 128 bytes (measured on 2026-11-11 with `sysctl hw.cachelinesize`), not the 64 common on x86. The value 128 covers both. The metadata is serialized by the same pool mutex and only one thread updates it at a time, so alignment has no benefit. Packing it tightly gives the accesses to the replacement policy and the counters better locality. See Design Document 2.12.
- **Cost:** Each frame latch is padded to a multiple of 128 bytes. `std::shared_mutex` is 168 bytes on the development machine (measured with `sizeof` on 2026-11-15, Apple clang with libc++), so an aligned latch takes 256 bytes, which is 88 more than without alignment, and the array for 256 frames is 64 KiB. In return there is no false sharing between the latches of different frames. The actual effect on scalability is not measured yet.
- **Current state:** `FrameLatchAddress` shows that the latch address of each frame is a multiple of 128, that adjacent addresses differ by at least 128, and that the start of the frame memory is a multiple of 4096. Comparing with and without alignment needs an unaligned version, and the method for building one is not decided yet. The alignment is a compile-time constant, so removing it means changing the build.
- **Rejected:** No alignment (whether false sharing is visible under reads from 8 threads is not measured yet, but there is no reason to accept it in advance); putting the metadata and the latch in one aligned struct (the metadata is already serialized by the pool mutex, and alignment would only waste memory); sizing with `std::hardware_destructive_interference_size` (the standard library of Apple clang has no reliable implementation).

### ADR-0035: Type names in the paged layer carry no engine prefix, and a table's page chain is called `TableHeap`

- **Decision:** The storage-layer types inside `strata::paged` do not take the `Paged` prefix. The engine adapter is the exception: `PagedEngine` is named for its role, beside `FlatFileEngine`. They are `Database`, `Catalog`, `DatabaseOptions` and `PageResult<T>`, and the files are `paged/database.h` and `paged/catalog.h`. The page chain of a table is called `TableHeap`, in the file `paged/table_heap.h`, and the documents call it the table heap. Test function names for the storage-layer types keep the `test_paged_` prefix; the execution-layer tests (`test_planner_`, `test_operators_`, `test_environment_`, `test_row_`) are named for the component under test.
- **Rationale:** The types are already inside the `paged` namespace, and `paged::PagedDatabase` repeats the engine name. Type names without the engine name keep a later rename of the engine from touching these types. `IPageStore`, `BufferManager`, `PageGuard` and `PageError` in the same namespace have no prefix, so the prefix would appear on only 4 types. `PageResult` and `PageError` share the same stem. For the page chain of a table, the "File" in `HeapFile` refers to a series of pages, while the real files in this project are `paged.db` and the CSVs of the flatfile engine. The object returned by `Database::Table(name)` is named after its internal arrangement, not after its role. `TableHeap` keeps the "heap" used by textbooks and PostgreSQL and drops "File". See Design Document 2.1, 2.2 and 2.11.
- **Cost:** Code outside `paged` has to write `paged::Database` and `paged::Catalog` to tell which engine is meant. In return the type names are independent of the engine name. `PageResult<T>` is also used for the return values of operations that are not page operations, for example table creation, and its semantics are narrower than those of `Result<T>`. In return its stem is consistent with `PageError`.
- **Current state:** The code and the documents use these names: `paged::Database`, `Catalog`, `DatabaseOptions`, `PageResult<T>` and `TableHeap`.
- **Rejected:** Keeping `HeapFile` ("File" is confused with the real files); `PageChain` (the name is tied to the current chained arrangement and would stop fitting if directory pages replace it later); keeping the `Paged` prefix (it repeats the namespace, and an engine rename would also rename 4 types).

### ADR-0036: Operators are pull-based row iterators, and `LIMIT` terminates early

- **Decision:** Each paged plan node corresponds to one `IOperator`, and `Next()` returns one row at a time. Scan, Filter, Project, the left side of a join and Limit stream their rows. Sort, Aggregate and the right side of a join are blocking: they read their whole input at the first `Next`. `LimitOperator` stops asking the child operator for rows after it has returned `limit` rows, and with a `limit` of 0 it requests no row. An operator has no open and close step. Building the operator tree reads no data row. The first use of a table opens its `TableHeap`, which walks the page chain once. See Design Document 2.13.
- **Rationale:** (1) With one row at a time, the output of a join needs no buffering, and memory is proportional only to the input of the blocking operators. flatfile solves the same problem by merging the join with the filter above it (ADR-0011). (2) `SELECT ... LIMIT k` reads only the pages needed to produce k rows. That is a measurable difference between paged and flatfile, and the benchmark workloads can show it. Opening a `TableHeap` at the first use of each table walks the whole page chain, which is O(P). This cost is paid once, and `RowCounts()` of `.open` has already paid it. (3) The iterator interface is the Volcano model of Graefe (Design Document 6). Open is merged into the first `Next`, because `HeapScan` holds no page pin between two `Next` calls and an operator has no resource that needs release at close.
- **Cost:** Each operator adds one virtual call and one `std::variant` return value per row, and the rows below `LIMIT` that are never read are never evaluated. flatfile computes the whole child plan first, so a division by 0 in row 100 is reported by flatfile and not by paged (Design Document 2.8). In return memory is proportional only to the input of the blocking operators, and `LIMIT` terminates early.
- **Current state:** The operators of Design Document 2.13 exist in `paged/operators.cpp`: `ScanOperator`, `FilterOperator`, `ProjectOperator`, `HashJoinOperator`, `NestedLoopJoinOperator`, `AggregateOperator`, `SortOperator` and `LimitOperator`. Building a tree reads no data row, and a finished operator never asks its child again (XU-13). `LIMIT 0` asks its child for nothing, also with an offset (XU-12). Every error below it is dropped, including the errors below a `Sort` or an `Aggregate`, while flatfile reports them (XI-19, ADR-0044). A positive `LIMIT` above a `Sort` makes the `Sort` read its whole input. XE-03 printed a first timing on the volume data (2026-11-20). It comes from one run of the test in a Release build on an Apple M4, with the median of 3 runs for the import and of 5 runs for each query workload. It is a first measurement, not a conclusion. `LIMIT 10` without `ORDER BY`: flatfile 0.483 ms, paged 0.008 ms. The four basic queries: flatfile 2.34 ms, paged 7.78 ms. Three-table join with `GROUP BY`: flatfile 6.67 ms, paged 12.33 ms. `LIMIT 10` behind `ORDER BY id`: flatfile 0.653 ms, paged 1.66 ms. Import of the three CSV files: flatfile 27.2 ms, paged 28.6 ms.
- **Rejected:** Vectorized execution that processes a batch of rows at a time (a batch boundary would need to be defined for every operator, and no measurement so far shows a need for it); every operator fully materializing its output (the number of rows after a join can reach n · m, as ADR-0011 notes); a push-based dataflow (early termination of `LIMIT` would need another cancellation mechanism).

### ADR-0037: Operators and constraint checks are pure logic that read through `IRowStream` and `ITableReader`

- **Decision:** `paged/operators`, `paged/mutation_planner` and `paged/row_keys` read data only through `IRowStream`, `ITableReader` and `domain::ICatalog`. The paged layer owns the first two interfaces. These files do not include `BufferManager`, `TableHeap`, `Database` or `Catalog`. `paged/heap_access` implements `IRowStream` and `ITableReader` and applies a `MutationPlan` to `TableHeap`. `tests/test_layering.cpp` checks this separation. See Design Document 2.1.
- **Rationale:** Pure logic stays separate from resource handling. Constraint checking is the part of the execution layer most prone to error, and the corresponding flatfile implementation is about 500 lines. It needs many test cases, and with the storage layer replaced by an in-memory `std::vector` the cases need no page, buffer pool or file. When an index arrives, an index lookup can become another entry point of the row layer, and the rules of the planner and the operators do not change (ADR-0051 makes it a second interface and leaves `ITableReader` as it is).
- **Cost:** The design adds one interface layer and one more move of a row, because `HeapScan` has already decoded the row into a `Row` and `StoredRow` wraps it once more. `StoredRow` and `ScanItem` have the same content and are defined separately, so the row layer does not include `table_heap.h`. In return the pure logic can be tested independently.
- **Current state:** The row layer (`row_stream.h`, `row_keys.h`, `operators.h`, `mutation_planner.h` and their sources) includes only `domain/`, `paged_types.h`, `tuple_codec.h` and its own files. `heap_access.h` implements `IRowStream` as `HeapRowStream` and `ITableReader` as `DatabaseTableReader` over `TableHeap` and `Database`. `StoredRow` and `ScanItem` are two types with the same content. XU-32 checks the include rules, among them that `bootstrap.cpp` is the only file outside `paged/` that includes a `paged/` header. The operators (XU-01 to XU-15) and the mutation planner (XU-16 to XU-27) run over in-memory `std::vector` streams, with no page, pool or file.
- **Rejected:** Operators using `TableHeap` directly (every test case would need to create pages and a pool); putting the interface in the Domain (only paged uses it and `Rid` is a paged concept, and ADR-0030 likewise lets the layer that uses an interface own it).

### ADR-0038: A write statement computes a change set before applying it, and a failed apply is undone from before-images

- **Decision:** `INSERT`, `UPDATE` and `DELETE` run in two phases. `PlanMutation` only reads. It checks all constraints and returns a `MutationPlan`, in which each `TableChange` holds the added rows and the updates and deletes, each with its before-image. Only `ApplyChangeSet` modifies `TableHeap`. It records an undo record immediately after each successful action, and an update that moves a row records the `Delete` and the `Insert` separately. On a failure it undoes the records in reverse order, and when an undo `Update` returns `kNoSpace` it uses `Delete` plus `Insert` instead. When the undo fails, the error message gets `; rollback failed: <message>` appended. See Design Document 2.13.
- **Rationale:** (1) One `UPDATE visitors SET username` rewrites the three tables visitors, stories and reactions, so a constraint violation has to be detected before any page is modified. ADR-0008 describes the same scenario. (2) An I/O failure midway through the apply, such as writing back a dirty victim page when the buffer pool replaces a page, has no WAL to handle it until the planned WAL exists. With undo, one I/O failure leaves a table inconsistent only when the undo also fails. Without undo the inconsistency is certain. (3) Computing the change set first lets tests of pure functions prove that a rejected statement changes no table, with no need to inspect pages.
- **Cost:** Every write statement keeps the selected rows and their before-images in memory, in a size proportional to the number of selected rows. Undo restores the content and the number of rows. It does not guarantee the `Rid` or the position of a row inside a page. When the undo fails, the table may contain partial changes. Until the planned WAL exists, nothing is guaranteed when the process terminates midway. In return pages are never touched on a constraint violation, and an I/O failure can be undone.
- **Current state:** `PlanMutation` returns a `MutationPlan` and touches no page. `ApplyChangeSet` applies it, records an undo entry after each successful action and undoes in reverse order on a failure. XU-16 to XU-27 test the planner. XI-04 shows that a rejected statement leaves the bytes of every page and `page_writes` unchanged, whether the cause is a constraint violation, an evaluation error or an overlong row. XI-05 fails the n-th `WritePage` for every n of an `UPDATE` with a cascade, a 300-row `INSERT` and a 150-row `DELETE`. The tables return to the state before the statement unless the failure came from the write-back. Three hand-made change sets cover the undo order, an undo `Update` that falls back to `Delete` plus `Insert`, and an update that moved a row. XI-06 fails a read inside the undo and gets `; rollback failed: <message>`.
- **Rejected:** Modifying while scanning (on a constraint violation part of the pages would already be changed, and the scan would also see its own modifications); no undo (one I/O failure would leave half a cascade and break the foreign key); writing the undo records into a file (that is a WAL, and the WAL is planned for later).

### ADR-0039: The paged constraint rules are implemented independently and cross-checked by the cross-engine equivalence tests

- **Decision:** `paged/mutation_planner` and `paged/operators` do not use the flatfile executor (`flat_file_executor.cpp`), and the shared rules are not moved into the Domain. The rules are specified in Design Document 2.3 and 2.5, and the error messages are identical word for word. The equivalence tests of Design Document 2.8 cross-check the two implementations.
- **Rationale:** (1) ADR-0001 decided that the two engines do not share an executor, because the project compares whole engines. (2) The flatfile executor is in the Infrastructure on the flatfile side, and `paged/` cannot include it without breaking the dependency direction. (3) Moving the shared rules into the Domain needs a change to `flat_file_executor.cpp`, which is already verified. flatfile is the baseline that paged is compared with, so it is not changed before the benchmarks are run, apart from the one change under Current state. (4) Two independent implementations make the equivalence tests meaningful, because an error in one does not automatically appear in the other.
- **Cost:** The constraint rules and error messages exist in two copies, about 500 lines of duplicated rules. When a rule changes, both places have to change, and the equivalence tests are the only synchronization mechanism. In return the baseline stays as it was, apart from the one change under Current state, and the two implementations check each other.
- **Current state:** `paged/mutation_planner.cpp` and `paged/operators.cpp` are separate from `flat_file_executor.cpp`, and the error messages are identical word for word. XI-18 to XI-20, XE-01 and XE-02 cross-check the two engines. One flatfile rule came from the cross-engine tests: `ComputeNewRows` in `src/flat_file_executor.cpp` keeps the stored cell when an assigned value equals it. Because `-0.0` equals `0.0`, `UPDATE zeros SET v = ABS(v)` keeps a stored `-0.0` when another cell of the row changes. Design Document 2.5 describes the rule, and XI-25 is the regression test. paged applies the same rule (XU-21).
- **Rejected:** Moving the rules into shared Domain functions (it needs a change to `flat_file_executor.cpp`, and with shared code the equivalence tests could not catch an error in the shared rule itself); `paged/` including the flatfile executor (it breaks the dependency direction, and `TableStore` assumes all rows are in memory).

### ADR-0040: The database-level reader-writer lock lives in `QueryService` and is shared by both engines

- **Decision:** `QueryService` holds one `std::shared_mutex`. `Execute(SelectStatement)` and `DescribeCatalog` take the shared lock. The other statements and `ImportCsv` take the exclusive lock. The lock covers bind and execute. It sits in the Application layer, and both engines share it. See Design Document 2.14.
- **Rationale:** The concurrency contract of the paged storage layer requires the caller to guarantee a single writer (Design Document 2.11), and its scope is many readers and a single writer. The lock sits above the engines, so both engines follow the same rule. flatfile has no in-process lock, and with this lock an entry point added later can handle several requests at the same time and still use both engines directly. The lock covers bind, so no other DDL statement can change the schema that the Binder sees before execution.
- **Cost:** Every reader waits during a write statement, and the I/O inside the statement runs while the lock is held. Concurrent writers are not supported. In return each statement is consistent as a whole, and with a single database-level lock there is no deadlock within a lock hierarchy.
- **Current state:** The lock is implemented in `application.h` and `application.cpp`. `ImportCsv` takes it before the check that a CSV source exists. XU-28 shows that two readers are inside the engine at the same time and that a second `SELECT` and `DescribeCatalog` finish while one `SELECT` is held. XU-29 shows that no call enters while a writer is inside, for each of the five writer kinds. XU-30 shows that bind and execute see the same catalog version while `CREATE TABLE` runs. XI-11 runs 8 readers and one writer (20 updates) through `QueryService` over both engines. The full suite passes under ThreadSanitizer. Fairness and the writer wait time are not measured yet.
- **Rejected:** One lock per table (a cross-table cascade would need several locks and a fixed acquisition order, which the current scope does not need); the lock inside the engines (each of the two engines would implement it, and flatfile has no in-process lock); locking only writes and not reads (a reader would read a page that the writer has half changed); multi-version concurrency control (MVCC, outside the current scope).

### ADR-0041: `.engine` is a session setting, and the data of the two engines in one directory does not interact

- **Decision:** `.engine [flatfile|paged]` sets the engine that `Cli` uses within the session. The setting is `flatfile` at every startup. `.open` opens according to the setting, and when a database is already open, `.engine` reopens the same directory. The flatfile data is `catalog.csv` and the CSV of each table, and the paged data is `paged.db`. The two do not interact, and a directory can hold both at the same time. When the opened result has no table and a file of the other engine (`catalog.csv` or `paged.db`) exists, `Bootstrap` puts one `note:` line into `OpenedDatabase::notes`, and `Cli` prints it. `.engine` is in the command name table of `Cli`, and a hint is given when the `.` is missing. See Design Document 3.6.
- **Rationale:** (1) The engine setting is not data. Writing it into the directory would make the same `.open` depend on which engine was used last time, so the result could not be reproduced. (2) With two sets of data in one directory, the same path can switch engines for comparison. (3) Switching reopens the directory without converting. The data of the two engines is not copied automatically, which avoids a silent data move, because conversion needs schema mapping and conflict handling. The `note:` keeps the user from thinking the data disappeared after switching engines.
- **Cost:** A directory may hold two copies of the data that are out of sync, and every startup returns to flatfile. In return switching engines needs no second path and no data conversion.
- **Current state:** Implemented in `repl.cpp` and `bootstrap.cpp`. The setting is `flatfile` at every start and is not saved (XI-13). `.open` follows the setting, and `.engine <other>` with a database open reopens the normalized directory with the other engine. The setting changes only when that open succeeds (XI-14). A failed reopen prints only `error: could not open <normalized directory>: <reason>`, with no `engine <name>` line, and the database and the setting stay as they were. Only the exact lowercase names are accepted, so `.engine PAGED` gives the usage error. Without the dot, `engine paged` gives `error: commands start with '.'; did you mean .engine`, and `.help` has one `.engine` line (XI-13). `Bootstrap` puts the `note:` line into `OpenedDatabase::notes`, and `Cli` prints it after the `loaded` line (XI-15). The demonstration of Design Document 3.6 runs on the real CLI executable (XI-16).
- **Rejected:** A command-line option `--engine` (the command-line usage stays unchanged, and the option can be added when needed); writing the engine setting into a file inside the directory (the first reason above); converting data automatically when switching (the third reason above).

### ADR-0042: The paged DDL covers `CREATE TABLE`, `ALTER TABLE ADD COLUMN`, `DROP TABLE` and import

- **Decision:** `PagedEngine` executes `CreateTableNode`, `AddColumnNode`, `DropTableNode` and `ImportTableNode` through `Database::CreateTable`, `AddColumn` and `DropTable`, and for an import through `CreateTable` and `InsertRows`. Each DDL statement is bound by the shared Binder and runs under the exclusive lock (ADR-0040). `ADD COLUMN` is ADR-0045 and `DROP TABLE` is ADR-0046. See Design Document 2.6 and 3.4.
- **Rationale:** The cross-engine equivalence tests and `.engine paged` need tables, and creating them through SQL verifies the whole path better than an internal API does. `.import` loads the same CSV into both engines with the same command, so the timing and Environment tests need no other loading tool. The two DDL statements came after the paged execution layer, because `ADD COLUMN` rewrites every row and `sys_columns`, and `DROP TABLE` needs a rule for reclaiming pages, and each needed a design of its own. With them the two engines accept the same statements, and the known differences of Design Document 2.8 no longer list a DDL statement.
- **Cost:** An `.import` that fails midway still leaves an empty table, although `DROP TABLE` now exists, because the import does not call it on failure. In return the import path stays one `CreateTable` and one `InsertRows`.
- **Current state:** `AddColumnNode` and `DropTableNode` are executed by paged (XI-08, XI-26 to XI-29), and `CREATE TABLE sys_x` is refused with `kUnsupported` (XI-19). `.import` first checks the tuple length of every row, so an overlong row creates no table. It then creates the table and writes the rows through `InsertRows`. An allocation failure midway leaves an empty table and a message that ends with `; table <name> was created` (XI-09). XE-01 imports the three CSV files of the volume data into both engines. The paged file exceeds 500 pages, so pages are evicted in a pool of 64 frames. XE-03 prints the first import timing (ADR-0036).
- **Rejected:** Tests creating tables through an internal API (the path differs from the user's, and the CLI could not switch engines to use them); `ALTER` and `DROP` in the same work as the first paged DDL (each needed its own design, ADR-0045 and ADR-0046); dropping the table of a failed `.import` (the cleanup needs the same disk that just failed, so it would add a second failure path to report).

### ADR-0043: paged writes dirty pages after each successful write statement and syncs at `Close`

- **Decision:** `BufferManager::WriteBackAll()` writes out every dirty frame and does not call `Sync`. `BufferManager::FlushAll()` calls `WriteBackAll()` and then `Sync`. `PagedEngine::Execute` calls `WriteBackAll()` after every successful write statement (`INSERT`, `UPDATE`, `DELETE`, `CREATE TABLE`, `ALTER TABLE`, `DROP TABLE`, `.import`) and before it returns. A failed statement, a query and a write statement whose change set is empty do not call it. When `WriteBackAll()` fails, `Execute` returns `kIo` with the message `<message>; statement was applied but not saved`, and the dirty pages stay in the buffer pool. `Database::Close()`, the destructor and `PagedEngine::Flush()` call `FlushAll()`. Before reopening the same directory, `Bootstrap` calls `PagedEngine::Flush()` on the current paged database and aborts the open when it fails. `PagedEngine` holds a `shared_ptr` to the directory lock. Its member order releases the lock only after the `Database` has written out. See Design Document 2.1, 2.15, 3.1 and 3.3.
- **Rationale:** (1) A process terminated by Ctrl-C or `kill` keeps the completed statements in flatfile, because every write statement there reaches the operating system. An interactive user of a SQL terminal expects the same of paged, and writing only at `Close` would lose every statement since the last write out. (2) `FlushAll` plus `Sync` (`F_FULLFSYNC` on macOS) after every statement costs one synchronization to the storage device per statement. The benchmarks would then measure the synchronization cost and not the engine difference. Neither flatfile nor paged calls `fsync` after a write statement, as the current state of ADR-0008 records for flatfile, and `WriteBackAll()` only writes. (3) A write statement runs under the exclusive lock of ADR-0040, so `WriteBackAll()` never runs at the same time as another `FlushAll()` or `WriteBackAll()`, which `BufferManager` requires. (4) Atomicity across several pages and durability on power loss belong to the planned Write-Ahead Log (WAL).
- **Cost:** Every write statement costs one write call per dirty page, and a failure can leave a statement applied in memory but not saved. A statement over several pages that is terminated during its write-back can leave a partial state in the file, because no WAL exists yet (Design Document 2.15). Writing out only at exit would carry the same risk only then, but would lose every statement since the last write out. In return completed statements survive Ctrl-C and `kill`, as in flatfile. The write-call cost per statement is not measured yet, and XE-03 reports the first timing.
- **Current state:** `WriteBackAll()` writes the dirty frames without `Sync`, and `FlushAll()` calls it and then `Sync` (PU-45). A query, a failed statement and a write statement whose change set is empty do not call `WriteBackAll()`. A change set is empty when no row is selected or every assignment equals the stored value. Such a statement neither saves the dirty pages of an earlier failed statement nor reports `statement was applied but not saved` (XI-24). XI-21 shows that after each write statement a copy of the store holds its effect while `CallCount(kSync)` stays unchanged. XI-22 shows that a failed write-back returns `<message>; statement was applied but not saved`, keeps the dirty pages and lets the next write save them. XI-10 shows that the data survive `Close` and a plain destruction. XI-19 shows that `paged.db` differs from its bytes at open after one write statement, before `Close`. Before reopening the same directory, `Bootstrap` calls `Flush()` without the `QueryService` lock. XI-12 shows that a table that was only in the pool is visible after the reopen. The branch that aborts the open when `Flush` fails has no test. Replacing a paged database through `.open <other directory>` or `.engine flatfile` does not flush first. A failed write-out is printed to standard error by the destructor, and the open is not aborted (Design Document 2.15).
- **Rejected:** Writing out only at `Close` (a process terminated by Ctrl-C or `kill` loses every statement since the last write out); `FlushAll` plus `Sync` after every statement (the second reason above).

### ADR-0044: Equivalence is defined over the result multiset, and the known differences are listed in the Design Document

- **Decision:** Design Document 2.8 defines two engines as equivalent when they agree on the result kind, the columns, the multiset of rows, `AffectedRows`, `tag`, the kind and message of errors, and the content of every table after a series of write statements. With `ORDER BY`, the sequence of sort keys must be identical, and the rows with equal keys form a multiset. The difference table in Design Document 2.8 lists the known and accepted differences, and behavior outside the differences must be identical.
- **Rationale:** (1) Without `ORDER BY` the row order is undefined (Design Document 2.3). Comparing row by row would make the file order of flatfile an implicit contract that paged has to imitate. (2) A stable sort preserves the input order, and the input order differs by engine, so the order among rows with equal sort keys cannot be compared. (3) The error messages are the contract of Design Document 2.5, and comparing them word for word can find a divergence between the rules of two independent implementations (ADR-0039). (4) The difference table states what it means for a test to pass.
- **Cost:** A multiset comparison cannot find out whether the order of rows is reasonable. The difference table is a list that needs maintenance, and when a difference is added, the Design Document and the tests are updated together. In return the tests are not bound to the internal row order of an engine.
- **Current state:** `FindResultDifference` and `EquivalenceRunner` in `tests/test_equivalence_support.cpp` implement the definition of Design Document 2.8. After every statement the runner compares the result kind, the columns, the rows, `AffectedRows`, `tag` and the error kind and message. Rows are compared as the sequence of sort keys with `ORDER BY` and as a multiset without it. After a write statement the runner also compares the catalogs and the content of every table, and checks that a rejected statement changed no table. A statement with `LIMIT` or `OFFSET` and no deterministic cut is reported as outside the comparable set. XI-18 (about 210 statements, LRU and 2Q, 4 frames), XI-20 (3 seeds, 1500 statements each), XE-01 and XE-02 find no difference outside the table. The difference table includes `LIMIT 0`: flatfile reports every error below a `LIMIT 0` and paged drops it, also below a `Sort` or an `Aggregate` (XI-19). The sign of a `DOUBLE` zero is not a difference, because both engines keep the stored cell when an assigned value equals it (ADR-0039). The `ZeroCorpus` statements of XI-18 read the sign back with `CAST(... AS TEXT)`, because the cell comparison cannot see it.
- **Rejected:** Row-by-row, order-by-order comparison (the first two reasons above); comparing only the row count (it cannot catch a wrong value); not comparing error messages (a divergence in the rules of two independent implementations appears only in the messages).

### ADR-0045: `ALTER TABLE ADD COLUMN` on paged copies the rows into a new page chain and then switches the catalog to it

- **Decision:** `Database::AddColumn` checks that the new `sys_columns` row fits in a tuple and that every row still fits in 4060 bytes with the default appended, which takes one scan and writes no page. It then reads the old chain with a `HeapScan` again and inserts each row with the default appended into a new chain, which starts at a page from `PageAllocator` and has the extended schema. After the last row it inserts the `sys_columns` row at the next position, updates `first_page` in the `sys_tables` row of the table, replaces the cached `TableHeap` and releases the old chain. The table keeps its `table_id`. A failed check is `kUnsupported` and leaves every page unchanged, and a failed step before the switch releases the new chain and deletes the `sys_columns` row if it was added. See Design Document 2.6 and 3.4.
- **Rationale:** (1) A tuple stores no column count (ADR-0027), so a chain holds tuples of one schema, and a `TableHeap` decodes with one schema. Rewriting in place would leave a chain of two kinds of tuples while the statement runs, and the undo of ADR-0038 restores a row with the schema that read it. (2) The new chain is invisible until `first_page` changes, so every failure before that write leaves the table as it was, and the old chain stays whole until the last step. (3) The copy compacts the table, which an in-place rewrite does not. (4) The Binder already rejects what would change a key or a foreign key (Design Document 2.4), so the catalog change is one appended row.
- **Cost:** The statement writes a second copy of the table before it frees the first, so the file grows by the size of the table at most while the statement runs, and the freed pages are reused later. Every `Rid` of the table changes. The statement reads the table twice and writes it once, whatever the default is. In return a failure before the switch needs no row-level undo. Without a WAL, the switch is two page writes that a crash can separate (Design Document 2.15).
- **Current state:** `Database::AddColumn` with `Catalog::CheckAddColumn` and `Catalog::CommitAddColumn` implement it. PI-16 adds an INT, a DOUBLE and a TEXT column to a table of 300 rows on about 13 pages and finds every row with its default after each call and after a reopen. PI-17 shows that a row of 4052 bytes accepts an INT column, that a row of 4053 bytes is refused as `kTooLarge` and a default of 4100 bytes as `kInvalidArgument`, and that the bytes of the store are the same after both refusals. PI-18 and XI-28 fail the n-th read, write and allocation of a statement on a table of about 20 pages in a pool of 4 frames: the table is then the old one or the new one, never a mix, and the new one comes with the message ending `; statement was applied but its pages were not reclaimed`. The fixed corpus of XI-18, the random runs of XI-20 and XE-02 give the same results on both engines, and DE-01 compares the statement with SQLite after a reopen. The window between the two catalog page writes is not tested, because a test cannot end the process between them.
- **Rejected:** An in-place rewrite with `TableHeap::Update`, and a delete plus insert for a row that grows (a chain of two schemas, and an undo that needs both); a schema version in the page header or in each tuple, with the default filled in at read time (the tuple format changes, every read path decodes by version, and `ADD COLUMN` would be O(1) while every later scan pays); a NULL for the old rows (the system has no NULL).

### ADR-0046: The pages of a dropped table go on a free list headed in the file header, and every page allocation takes from it first

- **Decision:** Page 0 holds `free_list_head` at offset 60, the first free page, and 0 when no page is free. A free page has `page_type` 3, `table_id` 0, no slots and a `next_page_id` that links the next free page. `PageAllocator::Allocate()` pops the head, or extends the file with `BufferManager::NewPage()` when the list is empty, and `TableHeap::Create` and the growth of a chain allocate only through it. `PageAllocator::Release(first_page)` walks a chain that no table owns, formats each page as a free page linked to the next, links the last page to the old head and then sets the head. `Database::DropTable` and `Database::AddColumn` release a chain after the catalog no longer names it. `Database::Open` walks the list and returns `kCorrupt` for a page past the end of the file, a repeated page or a page whose type is not 3, and `Allocate` returns `kCorrupt` for a successor below page 3. Adding the field did not change `format_version`, because a file written before it holds 0, an empty list; ADR-0048 raised the version to 2 for another reason. See Design Document 2.10 and 2.11.
- **Rationale:** (1) Without reuse, creating and dropping a table grows the file for good, which was the cost recorded in ADR-0024. (2) A free page has its own type, so a page cannot be free and owned at once without one of two walks noticing: a table scan rejects a free page in its chain (`CheckOwnership`), and the open-time walk rejects a table page in the list. That matters because an allocation over a page that a table still owns overwrites live rows. (3) The head sits in the file header, which the catalog already updates for `next_table_id`, so the allocator state is in one page. (4) A free page is empty, so no old tuple stays readable on it. (5) Releasing after the catalog change is the safe order: a failure in between wastes pages but never frees a page that a table names, and the head changes last, so a failed release leaves nothing half linked.
- **Cost:** `Release` reads and writes every page of the chain, O(P), and the pages it touches pass through the buffer pool. The file never shrinks. Without a WAL the page writes of a statement can reach the file in any order, and a crash can leave a list that names a page of a table or a table that names a free page; both states are reported as `kCorrupt` when the file is opened or the table is read, and nothing repairs them. In return a corrupt list cannot hand out a page that a live table owns without a check failing first.
- **Current state:** `PageAllocator` with `Allocate`, `Release` and `FreePages` implements the list. PU-50 releases a chain of 3 pages and takes the pages back in chain order with the page count unchanged. PU-52 shows that a chain that loops, reaches the file header, a system table page or a free page, or leaves the file, is `kCorrupt` and leaves the head as it was, PU-60 that a free page pointing below page 3 is refused by `Allocate`, and PU-53 fails the n-th read and write of `Allocate` and `Release` and finds a valid list after each. PI-15 opens files whose list leaves the file, holds a table page, loops, or links a heap page, and each is `kCorrupt` with the broken rule named. PI-19 drops one of three tables of 20 rows of 2000 bytes (about 10 pages each) and creates another with a new table id on the same pages, with the page count unchanged. PI-21 repeats create, add column and drop 40 times and the page count stays within 2 pages of its value after the first cycle. PE-04 drops the `scans` table of the volume data and loads it again, and the file grows by at most 2 pages. A crash between the page writes of a statement is not tested.
- **Rejected:** Never reclaiming (the cost of ADR-0024); linking the dropped chain into the list in O(1) without changing the pages (the pages keep their type, and `ADD COLUMN` makes a new chain with the same table id, so no check could tell a free page from a live one); a bitmap page of free pages (a second kind of page that must agree with the data pages, with no WAL); truncating the file (live pages would have to move, and their ids are stored in `sys_tables` and in the chain links).

### ADR-0047: Differential tests compare Strata with SQLite in a Python harness that runs the built CLI

- **Decision:** `tests/differential/differential.py` runs the statements of `tests/differential/corpus.sql` on three systems: the `sqlite3` module of Python, with an in-memory database and `PRAGMA foreign_keys = ON`, and `strata_cli` with `flatfile` and with `paged`. Each Strata statement runs in its own `strata_cli` process over a directory that the earlier statements wrote. The harness compares per value, and the SQLite value decides how the CLI text is read: an INT matches exactly, a DOUBLE to a relative 1e-9 (with an absolute floor of 1e-12 for values near zero), and a TEXT exactly. Rows compare as a multiset, or as a sequence when the corpus marks the order of an `ORDER BY` as total. Errors compare by class, constraint or other. A statement that differs from SQLite in a way that Design Document 2.3 lists carries a `-- differs: <area>` marker, and the harness fails both on an unmarked difference and on a marked statement that no longer differs. The two engines must agree with each other on every statement. `tests/differential/test_compare.py` tests the comparison. The build does not compile the harness; CTest runs it (ADR-0057).
- **Rationale:** (1) SQLite is the nearest reference for this subset of SQL, so a difference is either a documented choice or a defect in Strata. (2) A process per statement costs about 10 milliseconds, and it reopens the database after every statement, so the paged engine is checked for reading back its own file after each `ALTER TABLE` and `DROP TABLE`. (3) Python ships `sqlite3`, so no library is added to the build, and the build system stays as it is. (4) Reading the CLI text by the SQLite type avoids comparing text forms that differ by design (Design Document 2.3).
- **Cost:** Python 3.10 or later becomes a tool of the repository, though not a dependency of the build. A TEXT value with a tab or a line break cannot be told apart in the CLI output, so the corpus avoids them. The corpus is fixed, so it covers the cases that its authors thought of, where a generator would cover more of the input space. The result depends on the SQLite version in the Python that runs it.
- **Current state:** The corpus holds 185 statements, 23 of them marked, at least one for each of the 14 areas of Design Document 2.3. With the SQLite 3.54.1 of Python 3.15.2, DE-01 prints `differential: 185 statements, 23 expected differences, 0 unexpected`. DE-02 shows that deleting a marker, or marking a statement that agrees, makes the run fail. The statements include `ALTER TABLE ADD COLUMN` of each type, `DROP TABLE` and a table created again under a dropped name, so the paged engine is checked against SQLite after a reopen at every one of them. DU-01 to DU-07 cover the comparison, the parsing of the CLI output and of the corpus, the enforcement of the markers and the refusal of a nonzero exit status.
- **Rejected:** A C++ harness that links the SQLite library (a new dependency and a change to `CMakeLists.txt`, which needs approval); comparing the printed text of both systems (the text of a DOUBLE differs by design); a statement generator in Python (the equivalence tests of ADR-0044 already generate statements, and a second generator would copy the grammar); one `strata_cli` process for the whole corpus (each result would need a delimiter, and no statement would reopen the file).

### ADR-0048: The root page of an index is a column of `sys_tables`, and the file format version becomes 2

- **Decision:** `sys_tables` gets a sixth INT column, `index_root`, after `auto_increment_index`. A table whose primary key is an INT has one index, on the primary key, and `index_root` holds the page id of its root. Every other table holds 0, which cannot be a root because page 0 is the file header. `Catalog::CreateTable` allocates the first page of the heap, then the root page of the index, and writes both page ids into the one `sys_tables` row. `Catalog::CommitAddColumn` changes `first_page` and `index_root` in one row update. `Catalog::Load` returns `kCorrupt` for a nonzero `index_root` on a table whose primary key is not an INT, for 0 on a table whose primary key is an INT, and for a value below page 3 or past the end of the file. `format_version` is 2, and `Database::Open` refuses a file with another version as `kCorrupt` `format_version 1 is not supported (expected 2)`. Bytes 64 to 4095 of page 0 are reserved and zero. See Design Document 2.6 and 2.10.
- **Rationale:** (1) The root must be found at open without searching, and the catalog row already holds the first page of the heap. `ALTER TABLE ADD COLUMN` builds a new chain and a new tree beside the old ones (ADR-0053) and switches to both with one `sys_tables` row update that follows the `sys_columns` insert of ADR-0045, so the index adds no page write to the switch, which stays the two catalog pages of ADR-0045. (2) A tuple has no column count (ADR-0027), so a `sys_tables` row written with five columns cannot be decoded with six. That forces a version change, and the change is made once, now. The planned write-ahead log (WAL) is redo-only with no-steal buffering. It needs a page Log Sequence Number (LSN), which is already at offset 24 of every page under the CRC (ADR-0025), and a recovery start point, which can sit in a zero-initialized field of page 0 after offset 64 where zero means none, the argument of ADR-0046. It adds no page kind to `paged.db`, and index pages are whole pages with the same header, so the WAL needs no second format version. (3) The root never moves (ADR-0050), so only DDL rewrites the row. An insert that splits the root dirties index pages, and page 0 when a new page comes from the free list, but not a catalog page, which keeps the dirty set of a statement to heap and index pages when no-steal buffering has to hold it.
- **Cost:** A file of format version 1 cannot be opened and nothing upgrades it: the tables must be imported again. Whether a version 1 file exists outside the tests has not been checked. A second index kind on a table, such as a spatial index or an index on a `UNIQUE` column, needs another column or another system table, and so another version change; one kind exists now, so the column is the smaller change. In return the catalog has no third system table and no new undo path.
- **Current state:** Implemented. A new database gives its first INT-key table the pages 3 (heap) and 4 (root), a TEXT-key table gets 0, and a reopened catalog returns the same root (PI-34). `Catalog::Load` returns `kCorrupt` naming the table for a TEXT key with a root, an INT key with 0, a root of 2 and a root past the end of the file, and `Database::Index` returns `kCorrupt` for a root that is a heap page (PI-34). A new file has `format_version` 2 and zeros from offset 64 of page 0, and a file of version 1 or 3 is refused as `kCorrupt` with `format_version <n> is not supported (expected 2)` (PI-35). `ALTER TABLE ADD COLUMN` switches `first_page` and `index_root` in one row update, and a failure at any read, write or allocation leaves either the old table with its old index or the new table with its new index, both passing `CheckIndex` (PI-36).
- **Rejected:** A third system table `sys_indexes(table_id, column_position, root_page)` (it scales to several indexes, but it moves the first user page and the first user table id from 3 to 4, adds a table to `Load`, to the undo of every DDL statement and to a new file, and no second index exists to justify it); keeping version 1 and decoding old rows by tuple length (it works only if every row is rewritten at open); the root in the file header (one root per database, not per table); a root found by scanning the heap pages for an index page (O(P) at open).

### ADR-0049: An index node is one page of type 4, with the keys stored apart from the pointers

- **Decision:** `PageType::kIndexNode` is 4. A node is one page and keeps the 32-byte common header: `slot_count`, `free_end` and `dead_bytes` are 0, `next_page_id` is the right sibling of a leaf and `0xFFFFFFFF` on every other node, `table_id` names the owner, and `lsn` stays at offset 24 under the CRC. A node header of 16 bytes follows at offset 32: `level` (2 bytes, 0 for a leaf), `key_count` (2 bytes) and 12 reserved bytes of zero. Keys are signed 64-bit integers and are unique. A leaf stores `keys[289]` from offset 48 and `rids[289]` from offset 2360, a Rid being 6 bytes (page id and slot id). An internal node stores `keys[337]` from offset 48 and `children[338]` from offset 2744, 4 bytes each. The arrays are fixed regions of which the first `key_count` entries are valid. Key `i` of an internal node separates child `i`, whose keys are below it, from child `i+1`, whose keys are at or above it. A search is a binary search over the key array, read in place. The minimum occupancy of a later full delete is 144 keys for a leaf and 168 for an internal node (half of the capacity, rounded down). The constants are defined and not enforced. See Design Document 2.10 and 2.17.
- **Rationale:** (1) The capacity follows from 4096 - 48 = 4048 usable bytes. A leaf entry takes 8 + 6 = 14 bytes, so 289 entries use 4046 bytes. An internal node with n keys takes 8n + 4(n + 1) bytes, so n = 337 uses exactly 4048. (2) A search reads only keys, so keeping them contiguous shrinks what it touches: the 289 keys of a leaf span 2312 bytes, 18.1 cache lines of 128 bytes, and one line holds 16 keys, so the last 4 probes of a binary search share a line (log2 of 16). Interleaved 14-byte entries would put 9 entries on a line and 3 probes. The gain is small and has not been measured. (3) Frames and file offsets are multiples of 4096 (ADR-0025), so a node never crosses an operating system page, and the key array starts at 48, a multiple of 8, so every key is 8-byte aligned in its frame. Reads and writes stay byte by byte (ADR-0025), so the alignment is a property of the cache and not of correctness. (4) Search copies nothing: it reads the frame under the latch, a lookup copies one 6-byte Rid, and a range scan copies the qualifying entries of one leaf, at most 289 x 14 = 4046 bytes, before it releases the latch, because no pin is held between two `Next` calls (Design Document 2.13). (5) Nothing of a node lives outside its page, and a node carries the CRC, the page id and the LSN of every page, so the planned WAL and its torn page handling treat it like a heap page. The 12 reserved bytes may later take a field whose zero means absent. (6) With 337 keys an internal node has 338 children, so 30,000 rows need between ceil(30000 / 289) = 104 and ceil(30000 / 144) = 209 leaves and one internal root, a height of 2.
- **Cost:** An insert shifts the keys and the Rids that follow the position, up to 289 of each, with two moves of at most 2312 and 1734 bytes. A leaf wastes 2 bytes and every node 12 reserved bytes. The layout is fixed to 64-bit keys. The effect of the separate key array on search time has not been measured.
- **Current state:** Implemented in `btree_node.h` and `btree_node.cpp`, which take bytes or an `INodeSource` and nothing else; the layering test lists them in the byte layer. A leaf holds 289 keys and an internal node 337, the leaf key array ends at offset 2360 and the Rid array at 4094, and the child array ends at 4096 (PU-61). A full leaf of 289 splits into 145 and 144 keys, and a full internal node of 337 keys into 168 keys, the middle key passed up, and 168 keys (PU-65, PU-66). The effect of the separate key array on search time is not measured.
- **Rejected:** Interleaved key and Rid entries (a larger footprint for the search); a slot array with variable-length keys (only INT keys exist, and a slot adds 4 bytes per entry); one page type each for leaf and internal nodes (`level` already tells them apart, and one type keeps `VerifyHeader` and the ownership check to one rule); 32-bit keys (INT is 64 bits wide); a previous-leaf link (no scan needs it, and a split would have to latch the left neighbor as well).

### ADR-0050: Readers couple shared latches, writers split full nodes on the way down, and the root never moves

- **Decision:** A reader takes the shared latch of a child before it releases the latch of the parent. A range scan holds one shared latch at a time: it copies the qualifying entries of a leaf, releases the latch and follows `next_page_id`, and it stops after the leaf of its low bound when its high bound is below the separator that bounds that leaf from above. `Insert` descends with exclusive latches and splits every full node it meets, so the parent of a node being split always has room: the writer allocates the right sibling, moves the upper half, inserts the separator into the parent, continues in the half that holds the key and releases the parent. It also releases the parent when the child is not full. A full root splits in place: it keeps its page id, its halves move to two new pages and it becomes an internal node of one key, one level higher. `Delete` and `Replace` descend with shared latches and take an exclusive latch on the leaf only. Tree latches are taken from the root toward the leaf, then the file header inside `PageAllocator::Allocate`, then the new page, which extends the order of Design Document 2.14. A writer holds at most four latches (parent, child, file header, new page). A `BTree` needs one writer at a time, which the database-level lock provides. See Design Document 2.17.
- **Rationale:** (1) A reader can reach a node only through its parent or through the sibling link of its left neighbor. A writer that splits a node holds the exclusive latch of the node and of its parent until the sibling, the link and the separator are in place, so a reader sees the node before the split or after it, never between. This is the failure that the split protocol exists to prevent. The same latches prevent a data race on the bytes of a node. (2) All threads take tree latches from the root toward the leaf and from left to right along the leaves, and a scan holds two at most (a parent and its child while it descends) and one while it moves along the leaves, so no wait cycle forms. The file header and the new page come last in every path that takes them. (3) Splitting on the way down bounds the latches a writer holds by 4 whatever the height. Splitting from the bottom would hold the whole path, height + 2 latches, and the pool minimum of 4 frames (ADR-0028) could not run an insert in a tree of height 3. (4) A moved root would make the catalog row change on every root split (ADR-0048), and a reader would have to find the new root. (5) Every step that can fail (the fetch of the child, `Allocate`) comes before the first byte of the nodes it concerns changes, and the steps after it only write latched frames, so a failed insert leaves a valid tree, with at most some earlier splits that are valid on their own. For the planned redo-only WAL with no-steal buffering, a split is the changes to a node, its new sibling, its parent and sometimes page 0, all dirty in the pool until the statement commits, and a log of the after-images of the dirty pages of a statement carries the split whole. No separate undo of a split is needed, and no half split can reach the file ahead of its siblings.
- **Cost:** A full internal node is split on the way down even when the leaf below has room, so a tree may carry one internal split more than a bottom-up insert would make. Every insert takes the root exclusively, which costs readers a wait only when a writer runs beside them, and the database-level lock already excludes that at the engine level. The latches protect the storage contract and the ThreadSanitizer tests, and cost one latch per level. A midpoint split leaves leaves about half full under ascending keys, which an auto-increment key gives, so the index can be twice as large as a packed one; it has not been measured. The 4-frame bound leaves no spare frame, and PI-32 is the test that decides whether the pool minimum has to rise to 5 (it does not, see Current state). A delete leaves empty leaves in the chain (ADR-0053), and a scan that reaches past the leaf of its low bound reads each of them until it meets a key above its high bound, because only the leaf that the descent reached has a known upper bound.
- **Current state:** Implemented in `btree.h` and `btree.cpp`. Ascending keys 1 to 60000 give height 3 and 413 leaves, every leaf but the last with 145 keys (PI-26). 30000 random operations with capacities of 4 and 3, and 20000 with the defaults, agree with `std::map` for 3 seeds (PI-27). A find, a delete and a one-key scan each read 3 pages in that tree (PI-33). After a delete has emptied 700 of about 1000 leaves, a scan of an absent key inside the emptied keys reads one page per level, 10 in a tree of height 10, where a cursor that follows every empty leaf read 710, 361 and 11 pages for three such keys (PI-39). Measured on 2026-11-26 with a Release build and Apple clang 21.0.0 on an arm64 Mac (Darwin 25.5.0), in a paged database of 1,000,000 rows after `DELETE FROM t WHERE id >= 333333 AND id < 533333`: 1500 `SELECT` statements on absent keys in the deleted range used 5.17 s of user time before the rule and 0.15 s after it, and 1500 on keys outside the range used 0.14 s, each session including the open of the database (about 0.13 s, `/usr/bin/time -l`, one run each). A pool of 4 frames runs 2000 ascending inserts, which give height 10 with capacities of 4 and 3, then finds, deletes and a scan, with LRU and 2Q, on a new store and on one whose free list holds 2000 pages, so the pool minimum stays 4 (PI-32). A failure injected at each read, write and allocation of an insert leaves a valid tree (PI-30). One writer inserting 20000 keys beside four readers that find keys and scan ranges passes in the normal build and under ThreadSanitizer, which reports nothing (PI-31).
- **Rejected:** A bottom-up split with the path held (the latch count grows with the height); an optimistic descent that retries with a pessimistic one (two protocols to keep correct); one reader-writer mutex for the tree (a long scan would block every insert, and readers would not run beside a writer); a split that keeps sequential keys packed by giving the new right leaf only the new key (it leaves a one-key leaf, which the half-full minimum of a later full delete does not allow, and no measurement shows the need); a root that moves (the catalog row would change on every root split).

### ADR-0051: The row layer reads indexes through a new port, `IIndexReader`, and `ITableReader` stays as it is

- **Decision:** `IIndexReader` is an interface of the paged layer in `paged/index_reader.h`. `IndexedColumn(table)` returns the position of the indexed column, or no value for a table without an index or an unknown table. `ScanRange(table, range)` returns an `IRowStream` of the rows whose key lies in the `KeyRange`, in ascending key order. `Contains(table, key)` tells whether a row with the key exists, without reading the row, and returns a `ContainsResult`, a `std::variant<bool, domain::ExecutionError>`, so that a failed page read reaches the caller. `KeyRange` is a value type with an optional low and high bound and one inclusive flag for each. `DatabaseIndexReader` in `heap_access.cpp` implements the interface over `Database`. `BuildOperatorTree` and `PlanMutation` take a `const IIndexReader*` as their last parameter, null by default, and use table scans only when it is null. `ITableReader` has no new method. See Design Document 2.2 and 2.13.
- **Rationale:** (1) `ITableReader` is implemented by `DatabaseTableReader` and by the vector-backed fakes of the row layer tests. A new pure virtual method would change every one of them. A default body that falls back to a scan would hide whether an index was used, and a test could not tell the two apart. (2) A separate port keeps the row layer free of page types (ADR-0037) and lets a test double record what it was asked. (3) `Contains` serves the constraint checks that scan today: the duplicate check of a primary key and the parent check of a foreign key whose target is an indexed primary key. `ScanRange` serves queries and the `WHERE` of `UPDATE` and `DELETE`. (4) Both calls read pages only, so the planned WAL does not touch them.
- **Cost:** A caller holds two readers, and two call sites pass two arguments. That index scan and full scan return the same rows is a property that tests check (XI-30), not one the types give. In return the existing interface and its fakes do not change.
- **Current state:** Implemented for queries. `IIndexReader` is in `paged/index_reader.h`, `KeyRange` in `paged/key_range.h`, and `DatabaseIndexReader` in `heap_access.cpp`; `BuildOperatorTree` takes the reader as its last parameter, null by default, and `PagedEngine` passes one for every query (XU-34 with a fake port). `Contains` and `ScanRange` return `corrupt: ...` errors for a damaged index (PI-38). `PlanMutation` takes it as its last parameter too: an `INSERT` into a table whose primary key is indexed, with no `UNIQUE` column and no generated value, does not scan the table and asks `Contains` once per row, and a foreign key to an indexed primary key is checked by `Contains` without scanning the parent (XU-35, XI-31). `UPDATE` and `DELETE` read the rows of a `WHERE` that has a key range through `ScanRange`, in key order; an `UPDATE` that assigns a `UNIQUE` or a referenced column still scans the table, because its uniqueness check counts the rows that the `WHERE` does not select (XU-37). Generated statements with key predicates give the same results on both engines (XI-30), and the SQLite corpus (185 statements, 23 expected differences, 0 unexpected) passes with index scans active.
- **Rejected:** New methods on `ITableReader` (the first reason above); a reader that wraps `ITableReader` and recognizes predicates (it would have to see the plan); handing `Database` to the operators (it breaks ADR-0037, the row layer would include storage headers).

### ADR-0052: The operator builder picks the index scan from the predicate, and the plan and the Binder stay unchanged

- **Decision:** `BuildOperatorTree` treats a `FilterNode` whose child is a `ScanNode` as one unit. When `IIndexReader::IndexedColumn(table)` has a value, it calls the pure function `ExtractKeyRange(predicate, column)`. When the range has a bound, the scan under the filter reads through `ScanRange` and not through `Scan`, and the `FilterOperator` stays and evaluates the whole predicate on every row it receives. `ExtractKeyRange` walks the top-level `AND` tree and takes each conjunct of the form `column op literal` or `literal op column`, where `column` is the indexed column, `literal` is an INT and `op` is one of `=`, `<`, `<=`, `>`, `>=`. It skips every other conjunct, among them `<>`, `OR`, DOUBLE and TEXT literals and any expression such as `id + 0 = 5` or `ABS(id) = 5`. The bounds of the taken conjuncts are intersected, and contradictory bounds give an empty range. `PlanMutation` uses the same function for the `WHERE` of `UPDATE` and `DELETE`. See Design Document 2.13.
- **Rationale:** (1) Both engines run the same plan (ADR-0001), and a key range on `ScanNode` would be a field that flatfile must ignore. (2) The Binder puts a term that names one table directly above that table's scan (ADR-0009), also for one side of a join, so this is the shape that carries `id = 5` and `id >= 5 AND id < 9`. A filter above a join is not rewritten. (3) The filter stays, so extraction only narrows the rows. A missed conjunct costs speed, and a wrong row would need a bound that the predicate does not imply, which cannot come from top-level `AND` conjuncts. (4) An INT literal only, because an INT and a DOUBLE compare as DOUBLE (Design Document 2.3) and `id < 2.5` would need a rounding rule. A `-5` written without a blank is a negative literal in the parser, so `id = -5` qualifies, and `id = - 5` and `id = 2 + 3` are full scans because the Binder does no constant folding. (5) The rows of an index scan come in key order, and the order without `ORDER BY` is undefined (Design Document 2.3). (6) An index scan only reads pages, so the planned write-ahead log (WAL), redo-only with no-steal buffering, logs nothing for it and needs no change here; after a recovery the scan reads the redone pages as any query does.
- **Cost:** Rows outside the range are never evaluated, so an error that the predicate would raise on them is not reported: with `WHERE 10 / (id - 3) > 0 AND id = 5`, flatfile evaluates the first conjunct on the row with id 3 and reports a division by zero, and paged reads only the row with id 5. This is a new known difference (Design Document 2.8), of the kind of the early termination of ADR-0036, and the equivalence generator has to avoid or mark such statements. SQLite 3.54.1 behaves the same way, as Python's `sqlite3` module showed: with `id INTEGER PRIMARY KEY` and a row whose `v` is the smallest INT, `WHERE id = 1 AND abs(v) > 0` returns the row with id 1, and `WHERE abs(v) > 0` fails with `integer overflow`. A range that covers most of a table costs more than a full scan, because each entry is a random heap fetch, and no cost model chooses between the two. Constant folding is not done.
- **Current state:** Implemented for `SELECT`, `UPDATE` and `DELETE`. `ExtractKeyRange` takes the conjuncts `id = 5`, `5 = id`, `id < 5`, `5 < id`, `id = -5` and the intersections of such bounds, gives an empty range for `id = 3 AND id = 4`, and skips `<>`, `OR`, a DOUBLE literal and every expression (XU-33); a `Filter` over a `Scan` of a table with an index, also under a join, reads through the index and nothing else does (XU-34). The paged engine runs a point query, a range query, an insert that splits the last leaf, a relocating update, a delete and a join through the index in a pool of 4 frames with the results of a pool of 256 (XI-35). The mutation planner uses the range for the `WHERE` of `UPDATE` and `DELETE` (XU-37). Three seeds of 1500 generated statements, 60% of them with a key predicate, give the same results as flatfile and leave every index in agreement with its table (XI-30). A fixed corpus of 60 statements agrees on both engines after a row moves, after a key is deleted and inserted again, and after `ADD COLUMN` and `DROP TABLE` (XI-32). The known difference of this ADR's Cost is exercised by 6 statements that put `10 / (id - 3) > 0` before the key conjunct: flatfile reports `division by zero` and paged returns the rows of the key or none (XI-32). A point query of an existing key reads at most 3 pages in a table of more than 20 pages (XI-30, XE-04).
- **Rejected:** A key range on `ScanNode` (the plan is shared by both engines); removing the extracted conjuncts from the filter (a wrong extraction would change results without a trace); constant folding in the Binder (it changes every plan, flatfile's included, for one rewrite); a cost-based choice between index and full scan (there are no statistics, and the optimizer is out of scope).

### ADR-0053: Heap and index are changed together by one helper, and a changed Rid updates the index

- **Decision:** `heap_access.cpp` writes a table that has an index through one internal helper that pairs its `TableHeap` and its `BTree`. An insert runs `TableHeap::Insert`, then `BTree::Insert(key, rid)`. A delete runs `TableHeap::Delete(rid)`, then `BTree::Delete(key)`. An update in place changes nothing in the index while the key is the same, which holds for every direct `UPDATE`, because it never changes the primary key (Design Document 2.4). A cascade can change the key of a child whose foreign key column is also its primary key, and `ApplyChangeSet` then runs these updates as the deletes of all the old rows followed by the inserts of the new rows, each through the helper, so that a chain of renames (A to B and B to C) never meets a key that a later step frees. An update that returns `kNoSpace` runs as a delete and an insert in the heap and as `BTree::Replace(key, new_rid)`. The undo entries of `ApplyChangeSet` and `InsertRows` use the same helper, so undoing an insert deletes the key, and undoing a delete inserts the row and its key again with the new Rid. When the index step fails after the heap step succeeded, the helper undoes the heap step before it returns the error, and a failed undo appends `; rollback failed: <message>`. `Database::AddColumn` builds a new tree beside the new chain, inserts each copied row with its new Rid, switches both with one `sys_tables` row update and then releases the old chain and the pages of the old tree. `Database::DropTable` releases both. A delete only removes the key from its leaf: no node is merged, redistributed or freed. See Design Document 2.13 and 3.8.
- **Rationale:** (1) No `Rid` is kept across statements (ADR-0026) until an index exists. From then on the index keeps one, so every action that changes a Rid has to change the index in the same step. A Rid changes in three places: the relocation of an update, the re-insertion of a row by an undo, and the rewrite of `ALTER TABLE ADD COLUMN`. Compaction does not change a Rid. (2) One helper makes "heap and index agree" a property of one function and not of every call site, and the before-image undo of ADR-0038 stays valid because it goes through the same function. (3) A tree built beside the new chain keeps the property of ADR-0045 that nothing is visible until the catalog row changes, so a failure before the switch needs no row-level undo of the index. (4) All changes are page writes through guards, so a page-image log of the planned WAL needs no record type of its own for an index, and with no-steal buffering heap and index pages of a statement reach the file together.
- **Cost:** Every insert and delete costs O(log n) more page accesses, an insert dirties one more leaf and sometimes a split, and a statement of k rows dirties up to k leaves in addition to its heap pages, which the pool has to hold under no-steal buffering. Deleted keys leave space and possibly empty leaves until `ADD COLUMN` rebuilds the tree or `DROP TABLE` frees it. `ADD COLUMN` costs O(n log n) more. Write amplification has not been measured.
- **Current state:** Implemented in `heap_access.cpp` and `database.cpp`. After each of 2000 random statements on four tables, among them cascades that rename keys in chains, `CheckIndex` passes on every table, and it passes after a write that fails at each position of a cascade, a 300-row insert and a 150-row delete in a pool of 4 frames (XI-31). A missing index entry makes a delete or a relocating update fail with `corrupt: index of <table> has no entry for key <key>`, leaves the row in the table and leaves the missing key missing (XI-36). `ALTER TABLE ADD COLUMN` builds the new tree beside the new chain (PI-36), `DROP TABLE` puts the pages of the tree on the free list ahead of the chain (PI-37), and a delete empties leaves without freeing them (PI-28). The cost in page accesses and the write amplification have not been measured.
- **Rejected:** A hook inside `TableHeap` (the heap would know the tree, and the system tables have no index); rebuilding the index after each statement (O(n) per statement); maintaining the index in `PlanMutation` (the planner only reads, ADR-0038); changing the Rids in place during `ADD COLUMN` with `Replace` (the index would point into the new chain while the catalog still names the old one).

### ADR-0054: Index pages have their own page type, and the allocator frees an explicit list of pages

- **Decision:** `SlottedPage::VerifyHeader` accepts page types 0 to 4, and for type 4 it requires the three heap fields of the header to be 0. The node checks add the level, `key_count` not above the capacity and the owner `table_id`. `PageAllocator::ReleasePages(pages)` takes a vector of page ids that no table and no tree owns any more. Every page must be at or above `kFirstUserPage` (ADR-0055), inside the file, listed once, and a heap page or an index node. It formats each page as a free page linked to the next in list order, links the last page to the old head and sets the head last, with the failure ordering of `Release`. `Release(first_page)` stays for heap chains. `BTree::Pages()` returns every page of a tree from a walk that fails with `kCorrupt` on a page reached twice, a page of another table or a child whose level is not one below its parent. `Allocate` gives an index node a free page as it gives one to a heap page, and `FreePages` is unchanged. See Design Document 2.10, 2.11 and 2.17.
- **Rationale:** (1) `Release` follows `next_page_id`. A tree has no chain: its internal nodes point to children, and its leaves are linked only among themselves. An explicit list puts the knowledge of the structure in the structure, and the allocator keeps one job. (2) A type of its own for index nodes keeps the rule of ADR-0046, that a page cannot be free and owned at once without a check failing: the open-time walk rejects an index page on the free list because its type is not 3, and a tree that reaches a free page fails the node check. (3) `Release` and `ReleasePages` write whole pages and change the head last, so for the planned WAL they are page images like any other.
- **Cost:** `BTree::Pages()` reads every page of the tree before a `DROP TABLE` or an `ADD COLUMN` frees it, O(I) for I index pages, and holds the list in memory, 4 bytes per page, 209 leaves at most for 30,000 rows. A binary of the old format cannot read a page of type 4, which version 2 of the file already excludes (ADR-0048).
- **Current state:** `VerifyHeader` accepts page types 0 to 4 and refuses a type 4 page whose `slot_count`, `free_end` or `dead_bytes` is not 0 (PU-61, PU-54). `PageAllocator::ReleasePages` checks the whole list before it changes a page, so a refused list leaves every page and the head as they were; it returns `kInvalidArgument` for a page below 3 and `kCorrupt` for a page past the end, a page listed twice and a page that is not a heap page or an index node (PU-71, PU-72). `BTree::Pages()` is implemented, and `DROP TABLE` and `ALTER TABLE ADD COLUMN` list the pages of the tree before they change anything, so a damaged tree fails the statement as `kCorrupt` with no page changed, and `DROP TABLE` puts the pages of a valid tree on the free list ahead of the chain (PI-37, PI-38).
- **Rejected:** One page type each for leaves and internal nodes (`level` tells them apart); letting `Release` follow the leaf chain (it misses the internal nodes); a tree-aware `Release` (the allocator would include the node layout); a flag in the heap chain that marks index pages.

### ADR-0055: The system table ids and the first user page are defined once

- **Decision:** `paged_types.h` defines `kSysTablesId` as 1, `kSysColumnsId` as 2, `kFirstUserTableId` as 3, `kSysTablesPage` as 1, `kSysColumnsPage` as 2 and `kFirstUserPage` as 3. `catalog.cpp`, `database.cpp` and `page_allocator.cpp` use them in place of their own copies, `kMinimumPages` of `database.cpp` is `kFirstUserPage`, and the literal 3 in the `table_id` and `next_table_id` checks of `catalog.cpp` becomes `kFirstUserTableId`. No value changes. See Design Document 2.10.
- **Rationale:** The values exist today as `kSysTablesId` in `catalog.cpp`, the literals `{1, 2}` and the four constants `kSysTablesPage`, `kSysColumnsPage`, `kFirstUserTableId` and `kMinimumPages` in `database.cpp`, `kFirstUserPage` in `page_allocator.cpp`, and the literal 3 in the `table_id` check (`catalog.cpp:403`) and the `next_table_id` check (`catalog.cpp:548`). The first user table id and the first user page are two different facts that are equal by accident: the load check depends on the first, the rule that a page below the first user page is never released depends on the second. A system table added later moves both, and nothing links five places. The index work reads the first user page in the allocator (ADR-0054) and in the checks of `index_root` (ADR-0048), so it is the time to name it once. The planned WAL redoes whole pages and keeps the page Log Sequence Number (LSN) at offset 24 of every page, the system pages included, so it needs the page ids and no new constant; a recovery start point in page 0 (ADR-0048) is read at an offset after 64 and does not move these values.
- **Cost:** One header gets six constants and three source files change with no change of behavior. A later third system table still changes the file format, and these constants only make the places visible.
- **Current state:** Implemented. The six constants are in `paged_types.h`, and `catalog.cpp`, `database.cpp` and `page_allocator.cpp` use them. The existing allocator, catalog and database tests (PU-50 to PU-60, PI-15 and PI-19) pass unchanged.
- **Rejected:** A third system table now (ADR-0048); leaving the copies; one `constexpr` struct that holds the layout (no second user of the grouping).

### ADR-0056: `.dump index` reads the index through an optional Domain port, `IIndexInspector`

- **Decision:** `.dump index <table>` prints the shape of the index of a table of the open database. `domain::IIndexInspector` is a new interface of the Domain with `DescribeIndex(table)`, which returns an `IndexDescription` (table, column, height, node count, key count, the first 40 nodes in breadth-first order with level, page id, key count, first and last key and the right sibling, and the result of the check) or an `ExecutionError`. `PagedEngine` implements it beside `IEngine`. `QueryService::DescribeIndex(table)` takes the shared lock and calls it, and the engine's inspector reaches `QueryService` as a borrowed pointer given at construction, null for flatfile, which yields `kUnsupported` `the flatfile engine has no indexes`. `Cli` parses the command and prints the description. `IEngine` and `ICatalog` do not change. The check is `BTree::CheckInvariants` plus a scan of the heap that finds every key in the index with the same Rid. See Design Document 2.2 and 3.6.
- **Rationale:** (1) A user and a test need to see the tree and its verdict. (2) `IEngine` is the port at the plan layer (ADR-0001), and a method on it would be one that flatfile cannot implement. An optional second port leaves both engines as they are. (3) The command handler only parses and prints, and the application operation does the work, as for `.tables` and `.schema`. The description is data, so a test can check it without the terminal. (4) The command reads pages under the shared lock, which excludes a running statement, so under no-steal buffering it never sees the dirty pages of an uncommitted statement, and after a recovery of the planned WAL it checks the redone tree; it needs no log record.
- **Cost:** A second Domain interface and a defaulted constructor argument. The output is cut at 40 nodes with no option to print more. The check reads every page and does O(n log n) work under the shared lock, so writers wait for it.
- **Current state:** Implemented. `domain/index_inspector.h` holds `IIndexInspector`, `IndexDescription` and `IndexNodeDescription`. `PagedEngine::DescribeIndex` fills them from `BTree::Shape(40)` and `Database::CheckIndex`, and `QueryService::DescribeIndex` takes the shared lock (XU-36) and returns `kUnsupported` `the flatfile engine has no indexes` when no inspector was given. `Cli` prints the lines of Design Document 3.6 (XI-33) and the errors (XI-37). A root that fails the check of `BTree::Open` makes `.open` fail (XI-34), so `.dump index` meets other damage, such as a leaf that lost an entry, and its check line reports it (XI-33).
- **Rejected:** A method on `IEngine` (it changes the port that both engines implement); a `dynamic_cast` from `IEngine` (a hidden coupling that the types do not show); printing from `PagedEngine` to a stream (an Infrastructure class would format terminal output); a test-only hook with no command.

### ADR-0057: The differential tests are registered in CTest

- **Decision:** `CMakeLists.txt` calls `find_package(Python3 3.10 COMPONENTS Interpreter)`. When Python 3.10 or later is found, it registers two tests with `add_test`, run in the source directory, with the interpreter that `find_package` found (`Python3_EXECUTABLE`): `differential` runs it as `-I tests/differential/differential.py --cli <strata_cli>`, and `differential_unit` runs it as `-I -m unittest discover -s tests/differential -p "test_*.py"`. Both carry the test property `ENVIRONMENT` with `STRATA_CLI_PATH` set to the built `strata_cli`, so that the three end-to-end tests (DE-01 to DE-03) no longer skip. When no such interpreter is found, an older one included, it prints one line, `Python3 not found: the differential tests are not registered`, and registers nothing. Apart from the registration of the new source and test files, this is the only change to the build system in the index work, and the build does not compile the harness. See Design Document 3.6 and 5.1.
- **Rationale:** An index scan changes how the engine reads while the plan stays the same, and the comparison with SQLite is the regression check for that kind of change. Until now it ran only by hand (ADR-0047), so a change could pass `ctest` and still differ from SQLite. The corpus reopens the database for every statement (ADR-0047), so once the planned WAL replays its log at open, each statement of the same run starts from a replayed database and is checked against SQLite, with no change to the registration.
- **Cost:** `ctest` runs one more process per corpus statement and engine (about 10 milliseconds each, ADR-0047), and a machine without Python runs fewer tests without a failure. The minimum version 3.10 is the one that the harness needs (ADR-0047), so a machine whose only Python is older gets the same line and no test, and not a failing run. The total time has not been measured.
- **Current state:** `CMakeLists.txt` registers `differential` and `differential_unit` when Python 3.10 or later is found, both with `STRATA_CLI_PATH`. Run as registered, the harness prints `differential: 185 statements, 23 expected differences, 0 unexpected` and the 10 unit tests pass with none skipped. A configuration with `-DCMAKE_DISABLE_FIND_PACKAGE_Python3=ON` prints `Python3 not found: the differential tests are not registered` and registers only `strata_tests`. DE-04 is the check; DE-03 adds 28 statements to the corpus, at least 12 of them reads by key.
- **Rejected:** A C++ harness that links SQLite (ADR-0047); a custom target outside CTest (`ctest` would not run it); one registered test that runs only the script (the three end-to-end unit tests would keep skipping).

### ADR-0058: The result of `||` is at most 16 MiB

- **Decision:** `EvaluateBinary` in `src/expression.cpp` fails with the runtime error `result of || is longer than 16777216 bytes` when the two TEXT operands together are longer than 16,777,216 bytes (16 MiB). A result of exactly 16,777,216 bytes is allowed. Both engines evaluate `||` through this function, so the limit holds in both. No other TEXT operation has a limit.
- **Rationale:** The parser allows 499 `||` operators in one expression (Design Document 2.3), and a flatfile table can hold a TEXT value of a million characters, because only the paged engine caps a row, at 4060 bytes. `body || body || ...` with 499 terms over one 1,000,000-character value took 17.09 seconds and a peak resident set of 13,453 MB for a statement of 1.0 MB (a reviewer probe on flatfile, 2026-11-27, Release build, Apple silicon macOS). With the limit the same statement fails in 0.44 seconds with a peak of 148 MB (same machine and day).
- **Cost:** This gives up concatenated values above 16 MiB in the flatfile engine, which no test or example needs, and gets a bound on the memory of one `||`. The limit applies to each operator and not to a statement, so a result set of many rows can still hold many values of up to 16 MiB each.
- **Current state:** UT-110 checks a result of 16,777,216 bytes (allowed) and of 16,777,217 bytes in both operand orders (the runtime error above). The limit was measured only on the flatfile engine; the paged engine was not run with the probe.
- **Rejected:** A limit on the total size of the temporaries of a statement (the engines have no memory accounting); a limit on the number of `||` operators (it rejects short harmless chains and does not bound one operator over large values); no limit (a statement of 1.0 MB used 13 GB).

### ADR-0059: A first argument of `strata_cli` that starts with `-` is refused

- **Decision:** `strata_cli` prints `usage: strata_cli [<directory> [--parallel]]` to `stderr` and exits with 2 when its first argument starts with `-`, when it has more than two arguments, and when the second argument is not `--parallel`. A directory whose name starts with `-` is given as `./-name`.
- **Rationale:** The first argument is a directory, and the CLI creates a directory that does not exist (Design Document 3.1). `strata_cli -h` therefore created a directory named `-h` in the working directory and read from standard input, where a user who typed `-h` expected the usage. Only an argument that starts with `--` was refused.
- **Cost:** A directory whose name starts with a single `-` needs a `./` in front. In return a mistyped option never creates a directory.
- **Current state:** `strata_cli -h`, `strata_cli a b c`, `strata_cli a --bogus` and `strata_cli --parallel` exit with 2, print the usage and create nothing (ET-36).
- **Rejected:** A `--help` option that prints a longer text (no option exists to document, and the usage line is the whole interface); refusing only `-h` and `--help` (any other `-x` would still create a directory).
